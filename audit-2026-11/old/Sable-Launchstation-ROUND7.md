### LAUNCHSTATION-186 / On IOP, every "random" byte behind libsmb2's NTLM server challenge, preauth salt and SMB3 seal nonce comes from a 15-bit LCG seeded with uptime-seconds ⊕ a constant ⊕ a heap pointer / Category 6
- Locations: libsmb2 `lib/compat.c:507-520` (IOP `random()`), `lib/compat.c:523-531` + `:136` (`srandom`, single global state), `lib/compat.c:133-134` (`getpid()` = constant 27), `lib/init.c:400-410` (`smb2_random_bytes` fallback), `lib/init.c:427` (seed), `lib/init.c:440-443` (per-context consumption), `lib/libsmb2.c:5726` (`accept_cb` fresh context per connection), `lib/ntlmssp.c:1009-1010` (server challenge), `lib/smb3-seal.c:155` (CCM nonce); Launchstation-side selector: `iop/smbd/config.h` (defines no strong-source macro). (Paths under libsmb2/ are the fetched tree at a52c1571 + the two local patches; the mechanism was parent-verified at `compat.c:515` and `ntlmssp.c:1009`.)
- Problem: `config.h` selects none of `HAVE_ARC4RANDOM_BUF` / `HAVE_GETRANDOM` / `HAVE_DEV_URANDOM`, so the only `smb2_random_bytes` that can run is the fallback `p[i] = random() & 0xff`, which returns −1 to signal "fallback used" — a return no caller in the tree checks. On IOP, `random()` is a global LCG (`next*1103515245+12345`, 15 bits out per call), seeded per context with `time(NULL) ^ getpid() ^ heap-pointer` — uptime-seconds ⊕ the constant 27 ⊕ an address in the IOP's small heap — and **reseeded on every accepted connection into the one generator all contexts share**. That generator produces the NTLM server challenge transmitted in cleartext (directly under the file's own comment at `ntlmssp.c:1004-1008`: *"This has to be unpredictable: with a fixed challenge a captured response stays valid forever…"*), the preauth salt, and — when SMB3 encryption is negotiated — the AES-CCM nonce (`smb3-seal.c:155`, return ignored, directly under that file's own comment at :148-154 that the nonce *"has to come from the strong source and not from random()"*).
- Fix: Give the IOP build a real entropy source for these uses (e.g. seed from DEV9/SIO2/hardware noise + monotonic mixing, gathered once, never reseeded per connection), or fail closed where `smb2_random_bytes` reports fallback for the challenge and nonce uses. Justification for adding: this is the one round-7 fix that ADDS code; it is justified because the property at stake (challenge unpredictability, nonce uniqueness) is the stated purpose of both call sites in their own comments, and no deletion can supply it.
- Benefit: Challenge freshness stops resting on ≈(uptime ⊕ heap address) of entropy with cross-session sequence repetition; CCM nonce predictability/reuse risk removed.
- Effort: M / Risk: Medium (touches the auth path; needs care + the hardware test this VM cannot give) / Confidence: High on mechanism (READ, every link; parent-verified two links), Medium on practical exploitation (seed/state recovery not executed here) — INFERRED for exploitation only. Upstream status: all four libsmb2 files pristine upstream; the defect is the composition (upstream fallback + callers ignoring its signal + Launchstation's `config.h` offering no strong source), i.e. a defect of the local copy as configured.

### LAUNCHSTATION-188 / libsmb2 frees the file-notify list by recursion whose depth the remote server controls / Category 6
- Locations: libsmb2 `lib/libsmb2.c:4245-4252` (`free_smb2_file_notify_change_information`, recursive), built by `lib/libsmb2.c:4198-4244` (decoder), freed from `lib/libsmb2.c:4322-4325` and `lib/sync.c:1165`.
- Problem: One heap node is allocated per entry in a server-supplied change-notify buffer (decoder bounds each entry to ≥12 bytes, so node count = `rep->output_buffer_length / 12`, with the length taken from the reply — not the 4,096 bytes the client requested, `lib/libsmb2.c:116-117`). Freeing recurses one frame per node, so a malicious or broken server drives thousands of nested frames on the freeing thread's stack. Decode itself is iterative and safe.
- Fix: Iterative walk-and-free (a few lines, net-negative vs the recursion).
- Benefit: Removes a server-controlled stack-depth input from the client library.
- Effort: S / Risk: Low / Confidence: Medium (mechanism READ; no hostile-server execution here). Reachability: client-only API — in the shipped smbd build this is a GC candidate (see the updated residue), filed against the local copy for any PS2 client use of the fetched library. Upstream status: pristine upstream.

### LAUNCHSTATION-189 / Four libsmb2 client error paths leak their callback-data allocations / Category 6

- Effort: S / Risk: Low / Confidence: High (READ). Reachability: client-only, GC class in the shipped server (residue (a)); filed against the local copy as upstream-client defects. Upstream status: pristine upstream.

### LAUNCHSTATION-190 / libsmb2's AES-CCM tag verification uses early-exit `memcmp` / Category 6
- Locations: libsmb2 `lib/aes128ccm.c:174-190` (verify at :189); sole caller `lib/smb3-seal.c:211-216`.
- Problem: `aes128ccm_decrypt` decrypts in place, then finishes with `return memcmp(tmp, m, mlen);` — `memcmp` exits at the first differing byte, so verification time leaks the first-mismatch position of the 16-byte tag. The caller does check the result and refuses the PDU, so no unauthenticated plaintext is consumed; the residual is a timing oracle over a LAN against an IOP.
- Fix: Constant-time compare of the 16 tag bytes.
- Benefit: Removes the theoretical tag-forgery timing channel. Filed for completeness with exploitability explicitly doubted — not a practical forgery route.
- Effort: S / Risk: Low / Confidence: Medium on mechanism (READ), Low on practical exploitability. Upstream status: pristine upstream (non-OpenSSL body; the EVP body is not compiled here).
