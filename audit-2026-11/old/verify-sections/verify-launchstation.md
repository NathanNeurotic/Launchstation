## Full reasoning — every non-VERIFIED verdict

### LAUNCHSTATION-053 — VERIFIED-DRIFT

The mechanism re-derives exactly: `smbd_pread`/`smbd_pwrite` (`iop/smbd/smbd.c`) take a `uint64_t off` and pass it to `iomanX_lseek(fd, (int)off, FIO_SEEK_SET)` with no range check anywhere in either helper or in the `read_cmd`/`write_cmd` callers (`iop/smbd/smbd_fs.c:456,482`, which pass `req->offset` — a `uint64_t` field, libsmb2 `include/smb2/libsmb2.h:987,994` — straight through). The cast arithmetic is as filed: offset `0x1_0000_0000` becomes seek 0, and any offset ≥ 2³¹ becomes a negative seek. Only the citation moved: the helpers are at `smbd.c:150-160` (the casts at `:152` and `:158`), not the cited `:167-177` — those lines are `smbd_opendir`/`smbd_readdir`. Corrected locations: `iop/smbd/smbd.c:150-160`; callers as cited.

### LAUNCHSTATION-079 — WEAKENED

The headline (card-supplied superblock geometry is trusted without validation and reaches divisors, loop bounds and buffer offsets) holds, but two of its named divisor sinks do not hold as stated, and a third survives only on one target via a different route. The copy at `main.c:1391-1393` writes exactly 336 bytes (`r < 0x150`) over the start of `MCDevInfo`. Computing offsets from the struct as defined at `iop/vmcman/src/mcman-internal.h:298-328` (replicated and checked with `offsetof`): `pagesize` 40, `pages_per_cluster` 42, `blocksize` 44, `clusters_per_card` 48, `alloc_offset` 52, `backup_block1/2` 64/68, `ifc_list` 80, `bad_block_list` 208 — all inside the copy. But `cardtype` is at offset 336 (the first byte **not** copied; the code sets it explicitly at `main.c:1395`), `cluster_size` at 340, `FATentries_per_cluster` at 344 and `clusters_per_block` at 348 — all **outside** the copy. And `mcman_setdevspec` (`main.c:1334-1354`) runs before the copy and hard-sets `cluster_size = MCMAN_CLUSTERSIZE` (1024, `:1345`), `FATentries_per_cluster = MCMAN_CLUSTERFATENTRIES` (256, `:1349`) and `clusters_per_block = blocksize / pages_per_cluster` (`:1352`); the copy cannot change any of the three.

Consequences, sink by sink:

- **Refuted as stated:** the divide-by-zero via `cluster_size >> 9` at `main.c:3791-3792,3835`. `cluster_size` is invariably 1024 on every path through `mcman_setdevinfos`, so the divisor is invariably 2; no card image can make it 0 or 256 through this copy (or through `mcman_setdevspec`).
- **Narrowed:** `%`/`/` by `clusters_per_block` inside `mcman_setdevinfos` itself (`:1435,1439`), the `pmce[16]` index bound (`:3419,3520-3524`) and the `mcman_replacementcluster[16]` walk (`:3738-3742`). On the physical target `clusters_per_block` comes from hardware `McGetCardSpec` (`iop/vmcman/src/mcsio2.c:761`ff), not from the card image. On the VMC target it **is** indirectly card-influenced — but via the spec route, not the copy: `mcman_iomanx_backing_getcardspec` (`iop/vmcman/src/mciomanx_backing.c:178-200`) feeds the superblock's `blocksize`/`pagesize` into `mcman_setdevspec`, and the backing validator (`mciomanx_backing.c:107-141`) checks only magic, card type, `pagesize` ∈ {512, 528} and total file size — `blocksize` is unchecked, so a VMC superblock with `blocksize` 0 yields `clusters_per_block` 0 before the copy ever runs.
- **Verified as stated:** the sinks driven by fields the copy genuinely controls. Copied `pagesize` drives `McReadPage`'s ECC walk — `count = (pagesize + 127) >> 7` at `main.c:1186` iterated against the stack `eccbuf[32]` at `:1181` (loop at `:1204-1211`) — and `mcman_sparesize` at `:1328-1330`. Copied `pages_per_cluster` (with copied `pagesize`) drives the cluster reads at `:3766-3768` into `cl_data` slots whose stride is `MCMAN_CLUSTERSIZE` (1024) bytes (`main.c:3219-3223`), and the `mcman_pagedata[32]` indexing at `:3543,3553`, where `pageindex` accumulates `pages_per_cluster` per cluster. `backup_block1/2`, `alloc_offset`/`alloc_end` and `ifc_list` are likewise copied unchecked.

Verdict WEAKENED: the finding's core and several sinks stand, but it must be restated — `cluster_size` and (on the physical target) `clusters_per_block` are spec-derived constants, not superblock copy outputs, and the proposed fix's comparison list (`pages_per_cluster`, `cluster_size`, `FATentries_per_cluster`, `clusters_per_block`) would compare three fields the copy never touched.

### LAUNCHSTATION-080 — VERIFIED-DRIFT

The mechanism re-derives exactly: neither `McSetFATentry` (`main.c:3872-3902`) nor `McGetFATentry` (`main.c:3905-3931`) bounds `fat_index`; both compute `ifc_index = (fat_index / FATentries_per_cluster) / FATentries_per_cluster` (`:3880-3886` / `:3911-3915`) and index `mcdi->ifc_list[ifc_index]` (`:3886` / `:3917`), whose result is used as a cluster number for `McReadCluster`; card-fed walks feed the same path (`McReadDirEntry` at `:3813-3828`, masking only `& ~0x80000000` at `:3821`; `mcman_fatRseek` at `:1597-1643`). Two citation/arithmetic corrections: (1) `ifc_list` is `u32[32]` at `iop/vmcman/src/mcman-internal.h:312`, not the cited `:335` (that line is inside the `mcman_pagebuf` union); the exports are at `iop/vmcman/src/exports.tab:66,68` as cited. (2) The filed worked example is arithmetically wrong: for a PS2 card `FATentries_per_cluster` is 256 (`mcman_setdevspec`, `main.c:1349`; it is not superblock-controlled — offset 344, outside the -079 copy), so a FAT entry of `0x01000000` yields `ifc_index = (16777216 / 256) / 256 = 256`, not 4096 — a read 1,024 bytes from the start of `ifc_list` (≈896 bytes past its end, landing outside the 384-byte `MCDevInfo`), not "~16 KB past the array". The defect is unchanged (256 ≥ 32 is already out of bounds, and the masked card-fed maximum `0x7FFFFFFF` yields `ifc_index` = 32,768), but the example's numbers should be corrected wherever they are quoted.

### LAUNCHSTATION-189 — VERIFIED-DRIFT

Three of the four leak sites are exact: `smb2_pread_async` allocates `rd` (`calloc` at `lib/libsmb2.c:2001`) and returns `-EINVAL` on PDU-creation failure at `:2046-2050` without freeing it; `smb2_pwrite_async` does the same with `wr` (`:2122`, failure return `:2166-2170`); `smb2_ftruncate_async` does the same with `create_data` (`:3142`, failure return `:3160-3164`). The fourth site's mechanism also holds but its citation points at the neighbouring, correct path: the leaking return is the `smb2->user == NULL` validation at `lib/libsmb2.c:1405-1408`, which returns `-ENOMEM` without `free_c_data`, leaking the `connect_data` allocated at `:1388` plus the `server` strdup at `:1393` and the `share` strdup at `:1399`. The cited `:1409-1412` is the subsequent `strdup(smb2->user)` failure path, which **does** call `free_c_data` at `:1411`. Corrected location for site four: `lib/libsmb2.c:1405-1408`.
