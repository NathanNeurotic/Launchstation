## 2. Reasoning for every non-VERIFIED verdict

### LAUNCHSTATION-035 — VERIFIED-DRIFT
Substance fully re-derived: `pko_read_file` (`net_fio.c:363`) sends the requested `length` at `:391`, then at `:406` takes `nbytes = ntohl(readrly->nbytes)` from the host reply with no comparison to `length` anywhere in the function, and at `:412` calls `pko_recv_bytes(pko_fileio_sock, &buf[0], nbytes)`. `pko_recv_bytes` (`:86-102`) loops `recv` until exactly `bytes` bytes have landed in `buf`, so an over-claim writes past the caller's buffer; the return at `:417` reports the host's count. The sole caller, `net_fsys.c:188`, passes its own caller's buffer and size unaltered, so no caller-side guard defeats the finding. The `pko_accept_pkt` sub-claim also holds: a short header (`:121-125`) only `dbgprintf`s — a no-op without `DEBUG` (`:33-39`) — and parsing continues into the packet body at `:145-146`. Only the pinpoint lines drifted by one: the receive call is at **:412**, not :413, and `return nbytes` is at **:417**, not :418 (:418 is the unreachable second return).

### LAUNCHSTATION-036 — VERIFIED-DRIFT
The allocation census, the dashboard's double-hold (job buffer `dash_browser.c:559` allocated per listing while the resident `fb.files` at `:3376` stays live), the struct-by-struct copy at `:359-368`, and the `clipReserve` contrast all check out exactly; the census is if anything understated — an eleventh site exists at `src/filer_actions.c:1984` (`(MAX_ENTRY + 1) * sizeof(FILEINFO)`, not in the original list), and `src/filer_copy.c:915` is conditional (1 entry in the PSU-restore case). The size arithmetic does **not** survive re-measurement: the original's 384-byte `FILEINFO` (256 + 66 + "60, padded") matches neither model of the SDK struct. `sceMcTblGetDir` is 64 bytes by the in-tree copy (`iop/vmcman/include/mcman.h:24-33`, "size = 64"); host-compiling `FILEINFO` (`include/launchelf.h:201-206,560-565`) gives **388 bytes / 794,624 bytes per listing** if that struct's alignment is 4, and **448 bytes / 917,504 bytes** under the `aligned(64)` model the repo's own host tests use (`tests/test_file_browser_heap.py:42-43`) — the latter matching the repo's own source comments ("MAX_ENTRY entries are about 900 KB", `src/filer_actions.c:311`, `src/filer_browser.c:2007-2010`). The real SDK header (`<libmc.h>`, included at `launchelf.h:51`) is not in this tree, so the exact figure remains inferred — but the claimed ~768 KB is the one value neither model produces; the true figure is ~776 KiB or ~896 KiB, i.e. the waste is at least as large as claimed.

### LAUNCHSTATION-042 — WEAKENED
Narrower truth: the two URL parsers share a skeleton and one verbatim comment, but they are not "near-identical ~70-line functions." Measured: `nfsman_parse_url` is 52 lines, `smb2man_parse_url` is 40 lines. The near-identical part is only the host/IP prefix (scheme check modulo `nfs`/`smb`, host scan, bounded copy, the identical `// an IP address only: the driver has no DNS` line, `inet_addr` rejection). Everything after diverges: port parsing (shared `nfsman_number` helper vs an inline digit loop), the path terminator (`?` vs `/`), NFS's `uid=`/`gid=` query parsing (17 lines with no SMB counterpart), SMB's leading-slash skipping and its 127-byte TREE_CONNECT bound (no NFS counterpart). The devctl-connect wrappers are parallel in skeleton but differ in substance (credentials + latin-1 conversion vs seed/id). The root-listing name copies (`nfsman.c:992`, `smb2man.c:1256`) are genuinely parallel single lines inside parallel root branches. So: one shared ~20-line parsing core plus parallel skeletons — real duplication worth single-sourcing, but the claimed ~70 identical lines and the INFERRED ~100+ removable lines overstate what a merge could delete.

### LAUNCHSTATION-043 — WEAKENED
Narrower truth, pair by pair. (1) Receive loops: `usmb2.c:86-140` and `unfs4.c:120` `recv_reply_from_socket` are true near-duplicates (same reassembly skeleton, differing in id offset — MessageId at byte 28 vs XID at byte 4 — and record-mark handling). But `smbman`'s `GetSMBServerReply` (`smb.c:226`) is a different shape: it *sends* first, reads a NetBIOS session header, bounds the body to `SMB_buf` — and matches **no id at all**, so the title's "match its id, implemented three times" is false for the third implementation; only the bound-its-length concern is shared by all three. (2) MD4: `iop/smbman/md4.c` (182 lines, a Java-derived implementation per its header) and `iop/smb2man/usmb2/md4c.c` (240 lines, the RSA RFC 1320 reference) are two *independent* implementations of the same algorithm — functional duplication, not copied source that can be single-sourced by inclusion without choosing one implementation. (3) UTF-16: `smb.c:276,294` converts **ASCII↔UTF-16** (byte widening/narrowing); `usmb2/unicode.c` (204 lines) converts **UTF-8↔UTF-16** (`utf8_to_utf16` at `:116`, `utf16_to_utf8` at `:150`, with full code-point validation). They overlap in purpose but are not the same conversion and neither can replace the other. The uneven-hardening observation stands for the usmb2/unfs4 pair; the three-way single-sourcing programme in the fix does not follow as stated.

### LAUNCHSTATION-048 — WEAKENED (one sub-claim refuted outright)
First half — real code, no present effect: `net_fio.c:308-310` does test against `PKO_MAX_WRITE_SEGMENT` and assign `PKO_MAX_READ_SEGMENT`. But the two constants are **numerically identical** at this pin: `pko_pkt_write_req` and `pko_pkt_read_rly` (`iop/ps2host/hostlink.h:120-134`) are both packed structs of 4 + 2 + 4 + 4 = **14 bytes** (host-compiled check: `sizeof` 14 and 14), so both segments (`hostlink.h:276-277`) equal **1446**. No oversize segment can be emitted today; the claimed risk exists only if a future edit changes one struct and not the other — a latent identifier typo, not the "latent protocol violation" with a live size difference the text implies ("larger … whenever the read-reply struct is smaller" — it is not smaller; it is equal). Second half — **refuted**: the finding states the dirent name at `net_fio.c:648` is copied "without forcing termination," but the very next line defeats it:

```c
memcpy(dirent->name, dirrly->name, sizeof(dirent->name));   // net_fio.c:648
dirent->name[sizeof(dirent->name) - 1] = '\0';              // net_fio.c:649
```

The destination is terminated by construction. What survives of -048 is a one-identifier cleanup in the write path; the unterminated-string half does not exist at the pin.

### LAUNCHSTATION-051 — why the revised version verifies (recorded because the original did not)
For completeness on the revised text: (a) *Termination by construction once `strcat` survives* — the copy loop at `smb_fio.c:325-327` is bounded by `max_path - i - 2 > 0`, and `:330-331` unconditionally writes `'\\'` and `'\0'`, so every path that returns from `prepare_path` is terminated. (b) *Hazard confined to :311-312* — the only unterminated-string step is `strncpy` leaving `full_path` without a NUL if `smb_curdir` ever reaches `max_path - 3` chars, after which `strcat` over-reads; in practice `smb_curdir`'s only setter (`:859`, `strncpy(..., sizeof(smb_curdir) - 1)`) is fed from `prepare_path`'s own bounded, terminated output, so the hazard is idiom-level, exactly as narrowed. (c) *Dead strip* — at `:320`, `p2 = &path[strlen(path)]` points at the terminating `'\0'`, which is neither `'\\'` nor `'/'`, so the `while` at `:321-322` can never execute a single iteration for any input; the trailing-slash strip is unreachable as written (consequence: a trailing slash in `path` is copied by the loop and a second backslash appended at `:330` — benign, and part of why the dead code went unnoticed).
