### LAUNCHSTATION-185 — WEAKENED (narrower truth)
Re-derived by tracing `iop/xparam/src/xparam.c:30-45` exhaustively. Of the finding's two mechanisms, only one survives:
- **Survives:** `argc == 3` falls through both branches (`argc < 3` false, `3 < argc` false), so nothing beyond `SetDummyXparamValue()` runs. That control-flow fact is READ-true.
- **Refuted:** the claimed pair-loop drop ("for odd argc ≥ 5 the final complete pair is never applied — e.g. argc = 5 applies only argv[2..3]"). Pairs are consumed from index 2 as (2,3), (4,5), (6,7)…; the continuation test `i2 = i1 + 3 < argc` is exactly "the next pair's last index is in bounds". Trace: argc=4 → (2,3); argc=5 → (2,3) with argv[4] a lone trailing value that cannot form a complete pair under this indexing; argc=6 → (2,3),(4,5); argc=7 → (2,3),(4,5); argc=8 → (2,3),(4,5),(6,7). No complete pair is ever dropped; complete pairs exist only at even argc, and all are applied. The finding's example silently assumes pairs start at argv[1], which contradicts the code's own layout (argv[1] is the game-ID slot — `CheckGameID(argv[1])` at :32).
- **Reachability narrows it further:** the sole in-tree caller, `applyXPARAM` (`src/init.c:1355`), passes only a single gameID string (`strlen(gameID) + 1` bytes) — the explicit-pair path is never exercised in-tree at all. The surviving defect is therefore: an unexercised explicit-argument path has an `argc == 3` hole (name + ID + one unpaired value, for which there is arguably nothing valid to apply anyway). The proposed fix's loop-condition half (`i1 + 1 < argc`) should NOT be applied — the existing condition is correct, and changing it would make the loop read one argv slot past the last complete pair.
