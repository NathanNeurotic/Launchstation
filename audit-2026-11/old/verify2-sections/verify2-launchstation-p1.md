### LAUNCHSTATION-015 — WEAKENED
The pattern count is exact (863 grep hits over `src`+`include`+`iop` at this pin) and the cited chains exist verbatim (`src/config.c:544` allocation, the `%n`-measuring `sprintf` chain at `:548-712`, the `strcpy(c, LaunchElfDir); strcat(c, CNF);` assembly at `:732-782`). What does **not** survive is the concrete reachability claim for the config-save chain — "one over-long field overflows the heap buffer during save":
- At this pin the function carries the invariant in its own comment (`src/config.c:533-534`): *"Values are bounded by their source arrays; reserve extra space for key names, numeric fields and line endings."*
- Every `%s` argument in the chain is a fixed-size array inside `SETTING` (e.g. `LK_Path[SETTING_LK_COUNT][MAX_PATH]`, `usbkbd_file[MAX_PATH]`, the 64-byte `Misc_*` fields — `include/launchelf.h:281-340`), a `PathPad[30][MAX_PATH]` entry (`include/launchelf.h:548`), a static config-name string, or the SMB block whose `strlen` is explicitly added to the allocation (`smb_len`, `src/config.c:540-544`). No config-file value reaches this buffer except through those bounded arrays (parsing copies into the same fixed fields).
- So total string content is bounded by `sizeof(SETTING) + sizeof(PathPad) + smb_len` — exactly what is allocated — plus key names/numbers/line endings, for which the +8,192 B reserve exists. An overflow would require the format overhead alone to exceed 8,192 B, which the ~150 written lines do not approach.
Narrower truth: this is an unbounded-API hygiene / defence-in-depth issue (a future field added to `SETTING` without resizing the reserve, or a non-terminated source array, would silently become an overflow), not a demonstrated heap overflow on user-controlled data. The tree-wide 863-hit tail was not individually re-derived and is not endorsed here beyond the count.

### LAUNCHSTATION-030 — WEAKENED
Narrower truth: the allocation is real but mischaracterised, and the proposed saving does not follow. The `memalign(128, 512 * 1024)` at `src/dash_font.c:80` sits in `elisaAtlasReady()` — it is the texture for the Shift-JIS / ELISA glyph atlas, not scratch for the pre-rasterised dashboard faces. That texture is declared **512 × 1024** PSMT8 (`src/dash_font.c:91-92`), i.e. exactly 524,288 B: the allocation is precisely sized to its texture, and it is allocated lazily, only when an SJIS font is actually loaded, and reused via `elisa_tex.Mem` on later calls. The finding's sizing argument compares it to "the biggest single face atlas is 122,880 B" — but that is a different subsystem (the Roboto/EE face pixel data of LAUNCHSTATION-002, whose live textures are allocated separately at `src/dash_font.c:254` as `FONT_TEX_W × FONT_TEX_H` = 512 × 340). Sizing the ELISA arena down to a face size would corrupt SJIS title rendering. What survives: 512 KB of EE RAM is indeed held for SJIS rendering once triggered, for the life of the process; any saving would have to come from freeing/reducing the SJIS atlas itself, which the finding does not propose. Claimed "up to ~384 KB" saving: not supported.
