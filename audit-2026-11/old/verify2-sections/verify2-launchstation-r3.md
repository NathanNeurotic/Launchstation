## Reasoning for non-VERIFIED verdicts

### LAUNCHSTATION-070 — VERIFIED-DRIFT (supporting grep claim overstated; core claim and all locations stand)
The finding's load-bearing claims are exact: the two files, their line counts (413 + 168 = 581), the mmceman target's six-source list (`ps2.yaml:155-162`), `mmcedrv.c`'s own `IRX_ID` and export registration, and `mmcedrv_config.h` being included only by `mmcedrv.c`. What does **not** survive re-derivation is the sentence "Repo-wide grep for `mmcedrv`/`mmceigr` outside the files themselves and `.git` returns nothing." Actual grep hits outside the two files:
- `iop/mmceman/src/exports.tab:1-11` — the dead module's own export table (`DECLARE_EXPORT_TABLE(mmcedrv, 1, 1)`). It is not a live reference: the mmceman target in `ps2.yaml` has **no** `exports_tab` field, so this file is itself part of the dead module's remains (and would be orphaned by the proposed deletion — worth deleting alongside, which strengthens rather than weakens the finding).
- `iop/mmceman/include/mmcedrv_config.h` — the dead module's config header (existence acknowledged in the original's fix note; included only by `mmcedrv.c`, as stated).
- `iop/mmceman/include/module_debug.h:7` (`#define MODNAME "mmcedrv"`) and `iop/mmceman/include/irx_imports.h:22` (`#ifndef MMCEDRV`) — shared headers **included by live files** (`mmce_cmds.c:8`, `mmce_fs.c:10`, `mmce_sio2.c:15`, `mmceman.c:13`, `sio2man_hook.c:24`). These are name-string/ifdef traces of the module the live code was derived from, not build references to either dead file.
- `mmceigr` truly has zero hits outside itself.
None of these is a target, Makefile, or doc reference that builds either file, so the Cat-1 verdict (dead, deletable) is unchanged — but the "returns nothing" evidence sentence should be corrected to the list above.

### LAUNCHSTATION-072 — WEAKENED (one part refuted, four parts UNVERIFIABLE-HERE; only two of seven deletions are proven)
Per-part re-derivation against `/tmp/libsmb2-verify` + the smbd build list (`ps2.yaml:300-352`) and the smbd config (`iop/smbd/config.h`, which defines neither `HAVE_LIBQUIC` nor `HAVE_LIBRDMACM`):
- **(a) `quic.c` + `smbdirect.c` — VERIFIED deletable today.** `lib/quic.c:34-342` is wrapped entirely in `#ifdef HAVE_LIBQUIC`; `lib/smbdirect.c:50-1021` entirely in `#ifdef HAVE_LIBRDMACM`. With the smbd `config.h`, both are literally empty translation units. Deleting their two `ps2.yaml` lines (:315-316) cannot change the link.
- **(b) `aes_reference.c` — REFUTED as a "duplicate."** `lib/aes.c` is 36 lines and is a dispatcher: at :22-28 and in `AES128_ECB_encrypt` it includes/calls the Apple CommonCrypto implementation only `#if defined(__APPLE__) && defined(HAVE_COMMONCRYPTO_COMMONCRYPTOR_H)`, and otherwise falls back to `AES128_ECB_encrypt_reference` from `aes_reference.h` / `aes_reference.c` (560 lines — the only full AES implementation in the tree for non-Apple builds). The IOP build is non-Apple, so `aes_reference.c` (`ps2.yaml:301`) is the server's **only** AES and must **not** be deleted. The original's "second (reference) AES implementation / duplicate of aes.c" classification is backwards: `aes.c` is the shim, `aes_reference.c` is the implementation.
- **(c) `sync.c` + `smb2-share-enum.c` — UNVERIFIABLE-HERE.** No reference from first-party `smbd.c`/`smbd_fs.c` (grep, confirmed), but intra-library references in client-only code inside otherwise-compiled units do exist: `sync.c`'s `smb2_share_enum_sync` (:1229-1248) calls `smb2_share_enum_async` in `smb2-share-enum.c`, and `lib/libsmb2.c`'s client function `smb2_notify_change_async` calls `sync.c`'s `smb2_open`/`smb2_close` (`libsmb2.c:4408-4417`). Whether those client-only callers are themselves garbage-collected under the target's `--gc-sections` + `-ffunction-sections` (`ps2.yaml:357-358`) can only be settled by the link test, which cannot run in this VM (no IOP toolchain build of smbd performed here).
- **(d) `smb2-data-security-descriptor.c` + `smb2-data-reparse-point.c` — UNVERIFIABLE-HERE.** Likewise referenced from client-side code in compiled units: security-descriptor decode from `lib/smb2-cmd-query-info.c:723` and encode/size from `lib/smb2-cmd-set-info.c:251,266`; reparse decode/encode from `lib/libsmb2.c:1576,3405` and `lib/smb2-cmd-ioctl.c:420`. (Note the query-info caller sits in a reply-encoding function, so this part is, if anything, *less* clearly dead than the original assumed — another reason the link test is mandatory.) Same `--gc-sections` + link-test dependency as (c).
- **What drives the verdict:** (b) alone falsifies the finding as filed ("drop the seven lines"), and (c)/(d) — the parts marked UNVERIFIABLE-HERE above — mean four more of the seven deletions are unproven at this pin. The narrower truth that survives: **2 of 54→53 vendored units (`quic.c`, `smbdirect.c`) are provably empty and deletable today; `aes_reference.c` must stay; the remaining four deletions rest entirely on a link test that has not been run.**
