## 2. Reasoning for every non-VERIFIED verdict

### LAUNCHSTATION-120 — VERIFIED-DRIFT

The headline defect is proven by pure control-flow arithmetic at `src/filer.c:1766-1782`: the loop runs `rv = 0..size` inclusive, substitutes a synthetic 0x0a at `rv == size`, and each successful probe increments `hostcount`; the return at :1782 is unconditionally `hostcount - 1`. For a list with no trailing newline there is no phantom entry to cancel, so the last real entry is dropped and a one-entry list returns 0. That stands exactly as filed.

The drift is in one sub-claim: "an empty list returns −1." A zero-byte `elflist.txt` never reaches that return — the seek path at `src/filer.c:1748-1754` returns 0 early when `size <= 0`. A −1 return is reachable only from a *non-empty* file whose lines all produce no entries (e.g. a file containing a single newline, and only if empty lines add no entry via the open/dopen probes). Corrected statement: empty (zero-byte) list → 0; no-entry non-empty list → −1; any list without a trailing newline → last entry dropped.

### LAUNCHSTATION-122 — WEAKENED

Narrower truth, established by reading the modal keyboard the finding's mechanism depends on (`src/dash_widgets.c:442-591`):

- There is **no clamp-to-`max_len` on confirm**. `modalKeyboard` never truncates `buf` on the success path; the only truncation to `max_len + 1` is at `dash_widgets.c:587` — `if (!result) dashStrCopy(buf, orig, max_len + 1);` — i.e. on **cancel**, and `actRenameGame` discards `buf` entirely when the keyboard returns 0 (`src/dash_hdd.c:711`). A user who opens a >31-char title and confirms without editing hits the `!strcmp(name, p->game.Name)` early return with the title intact; a user who deletes characters and confirms renames to exactly what remains, not to a forced 31 chars.
- What the 31 cap actually does: `kbInsert` (`dash_widgets.c:341-350`) refuses insertions while `strlen(buf) >= max_len`, and the on-screen counter displays `strlen/31`. So a long title cannot be *extended*, and characters must be deleted down below 31 before any insertion is accepted — an editing constraint, not silent data loss on rename.

The buffer/cap mismatch (65-byte buffer, 31-char keyboard cap, apparently carried over from the partition rename) is real, and passing `sizeof(name) - 1` remains a reasonable fix — but the filed consequence ("renaming a game whose title exceeds 31 characters silently cuts it to 31 even if the user only edited its start") does not occur in the code at the pin.

### LAUNCHSTATION-127 — REFUTED

The unchecked-`snprintf` observation is literally true, but the finding's problem — truncation occurring and the code proceeding with a wrong query / malformed JSON body — is defeated by the callers' own checked bounds, which cap every input strictly below every destination at the three cited sites:

- All variable inputs pass through `q_escape` / `json_escape` first, and **both fail (-1) rather than truncate** (`src/cloud_google.c` `q_escape` and `json_escape` bodies: `if (*p) return -1;` after the bounded loop), and all three sites check those returns and abort. Resulting caps: escaped name ≤ 511 chars (buffer `MAX_NAME * 2` = 512), escaped parent ≤ 383 chars (buffer `CLOUD_ID_MAX * 2` = 384, `CLOUD_ID_MAX` = 192 at :30), sha256 ≤ 64 chars (every caller passes a local `sha256[65]`; `drive_find_child` call sites :861, :1213, :1310).
- `drive_find_child` (:705-748): worst-case query = 383 + 511 + 64 + ≈151 literal = ≈1,109 < `query[1280]`; worst-case path = encoded ≤ 3,839 (itself produced by the checked `append_url`, whose return *is* tested at this site) + ≈74 literal = ≈3,913 < `path[4352]`.
- `drive_create_folder` (:1185-1195): worst-case body = 511 + 383 + ≈80 literal = ≈974 < `body[1024]`.
- `drive_upload_file` (:1272-1326): worst-case body = 511 + 383 + 64 + ≈60 literal = ≈1,018 < `body[1280]`.

Since no input combination that survives the checked escapes can reach any of these buffers' limits, the snprintf calls cannot truncate, and the claimed consequences (silently searching for the wrong folder, sending a malformed JSON body) cannot occur at these sites. What survives is only a style observation — the returns are unchecked, unlike the two correct sites at :878-901 and :968-975 — with no reachable defect behind it.
