### R4-R1 — LAUNCHSTATION-064 (smbd replacement `calloc`/`malloc` size arithmetic): local defect stands, remote reachability REFUTED — downgraded to latent hardening

Round 3 filed the missing overflow checks in `iop/smbd/smbd.c:38-66` with reachability INFERRED: "whether a remote-reachable libsmb2 call site actually feeds attacker-sized `n`/`size` into `calloc`". The census is now complete. Every `calloc` call site in the 53 compiled libsmb2 sources falls into one of these shapes (READ, full grep census):

- `calloc(1, sizeof(...))` — the dominant shape, including every server request decoder (`smb2-cmd-*.c`: `req = calloc(1, sizeof(*req))`) and every handler-adjacent struct;
- `calloc(len, sizeof(uint8_t))` — the per-command encode helpers, where `len` is a fixed command-struct size and the element size is 1;
- `calloc(1, len)` / `calloc(1, alloc_len)` — `spnego-wrapper.c` (token assembly from an already-received PDU), `smb2-cmd-query-directory.c:291`, `smb2-cmd-query-info.c:169` (`len + 1024`, client reply path);
- `calloc(size, 1)` — `alloc.c:93,109` (`smb2_alloc_init`/`smb2_alloc_data`), element size 1;
- the **one** arithmetic-sensitive site in the library, the copychunk input builder, is explicitly overflow-guarded upstream before it allocates: `libsmb2.c:3718` rejects `chunk_count > ((UINT32_MAX - 32) / 24)`, then `calloc(*input_count, sizeof(uint8_t))` (:3723) and `calloc(chunk_count, sizeof(struct smb2_srv_copychunk))` (:3945) — and that whole path is the *client* server-side-copy API, not reachable from smbd's server dispatch.

There is **no** call site of the form `calloc(n, size)` with both operands variable and greater than 1. On the `malloc` side, every wire-influenced length is bounded before allocation by the receive cap (see R4-R2: hard maximum 16 MiB in `include/libsmb2-private.h:352`, and 128 KiB in smbd's configuration) — three orders of magnitude below the ~2³¹ needed to wrap `size + 8` in `smbd.c`'s `int` parameter. **Verdict:** the wrap in `calloc`'s `n * size` and in `malloc`'s `size + 8` cannot be reached by any caller at this pin, remote or local. The 3-line guard round 3 proposed remains harmless insurance and is still the tidy thing to add while touching the file, but -064 should no longer be counted as a reachable Cat 6 defect — it is a latent-hardening note on a choke point whose callers are all, today, incapable of feeding it a dangerous size. Confidence in the refutation: High (complete call-site census, READ).

### R4-R2 — LAUNCHSTATION-065 (`write_cmd` never caps the transfer length): REFUTED as a security finding — the bound exists, one layer down and coarser than advertised

Round 3's open question was whether libsmb2's PDU layer enforces the negotiated `server.max_write_size = SMBD_MAX_IO` (64 KiB, `iop/smbd/smbd_fs.c:997`) on inbound writes. Answer, in three parts (all READ):

1. **The exact negotiated cap is NOT enforced on inbound WRITE.** Nothing in `smb2-cmd-write.c`'s server decode compares `req->length` to `smb2->max_write_size`. To that extent round 3's suspicion was correct.
2. **But two coarser bounds make the feared outcomes impossible.** (a) The receive path rejects any PDU whose peer-supplied session length exceeds `smb2_recv_pdu_cap()` before allocating for it (`lib/socket.c:568-578`, applied again per-fragment at `socket.c:860` and to transform PDUs at `lib/smb3-seal.c:231`). The cap is `max(max_read_size, max_write_size) + 64 KiB slack`, hard-capped at `SMB2_MAX_PDU_SIZE` = 16 MiB (`include/libsmb2-private.h:352-368`). (b) The write decoder itself rejects any request whose declared data extends past the received PDU (`smb2-cmd-write.c:293-300`, "Write data extends beyond end of PDU"), so `req->length` can never exceed bytes actually received.
3. **In smbd's configuration the arithmetic is small.** `smbd_serve` sets all three server sizes to `SMBD_MAX_IO` (65,536) at `smbd_fs.c:997`, and the library copies them into each connection's context at accept time, before the first PDU is processed (`lib/libsmb2.c:5909-5911`). The receive cap for every smbd connection is therefore 65,536 + 65,536 = **131,072 bytes**. `write_cmd`'s `(int)req->length` (`smbd_fs.c`, `write_cmd`) can never go negative and can never name more than ~128 KiB; `smbd_pwrite` receives a sane `int` on every path.

**Residual, honestly stated:** a client may send a single WRITE of up to ~128 KiB against an advertised 64 KiB maximum — the 64 KiB of slack is the library's deliberate headroom for headers/transform overhead, applied to the whole PDU, not per-field. That is a spec-conformance wart (a strict server would answer `STATUS_INVALID_PARAMETER` for `length > max_write_size`), not a memory-safety or data-integrity defect: the write lands on a memory card through the already-validated `smbd_pwrite`, offset handling unchanged (and its 32-bit offset truncation is LAUNCHSTATION-053, already filed). Round 3's proposed one-line reject in `write_cmd` remains available if the maintainer wants strict conformance, but -065's Cat 6 framing does not survive contact with the library: **withdrawn as a security finding, retained as this note.** Confidence: High (READ, full chain cited).

### R4-R3 — LAUNCHSTATION-072 (seven libsmb2 lines fetched and compiled for a server-only module): SPLIT verdict — 2 provably free to delete, 4 GC-dependent, 1 must NOT be deleted

Round 3's stated unknown was "whether intra-library references exist to the deletion candidates". They do — for five of the seven files. Method: symbol-definition extraction over the candidate files, then reference search across the other 52 compiled libsmb2 sources, all library headers, and first-party `smbd.c`/`smbd_fs.c` (script preserved in the round's working notes; every positive hit below was then read in context).

**(a) `quic.c` (`ps2.yaml:315`) and `smbdirect.c` (`ps2.yaml:316`) — CONFIRMED, and stronger than round 3 knew: both are empty translation units in this build.** The entire body of `quic.c` sits under `#ifdef HAVE_LIBQUIC` (`quic.c:34` … `#endif /* HAVE_LIBQUIC */` at :342); `smbdirect.c` likewise under `#ifdef HAVE_LIBRDMACM` (:50 … :1021). Neither macro is defined by `iop/smbd/config.h` (round 3 read it in full; re-grepped this round). Every call site is under the same guards: all `smb2_quic_*`/`smb2_rdma_*` uses in `lib/socket.c` (lines 198, 203, 345, 350, 1242, 1366, 1399, 1649, 1683, 1715, 1740, 1823, 1865), `lib/libsmb2.c` (1124, 1296, 5787, 5916) and `lib/init.c` (194, 201) are inside `#ifdef HAVE_LIBQUIC`/`#ifdef HAVE_LIBRDMACM` blocks; the only unguarded uses anywhere are `smb2_quic_reset`/`smb2_rdma_reset` in `lib/init.c:476-477`, which in the no-library case are preprocessor no-ops (`#define smb2_quic_reset(smb2) do { } while (0)`, `include/libsmb2-private.h:484` and :501). Deleting the two `ps2.yaml` lines cannot break the link — there is nothing in either object file to reference or be referenced. **These two lines are free to delete today, no link test needed for them specifically.**

**(b) `aes_reference.c` (`ps2.yaml:301`) — REFUTED. It is not a duplicate of `aes.c`, and deleting it breaks the build.** Round 3's inventory classified it "probable duplicate" (INFERRED, from filenames). In fact `aes.c` is 36 lines: a platform dispatcher whose only function, `AES128_ECB_encrypt`, calls `AES128_ECB_encrypt_apple` on Apple builds and **`AES128_ECB_encrypt_reference` everywhere else** (`aes.c:27-34`) — i.e. on the PS2 build, the 560-line tiny-AES implementation in `aes_reference.c` *is* the AES the server's signing/sealing runs on (via `aes128ccm.c`, which calls `AES128_ECB_encrypt`). Remove the line and the link fails with an undefined `AES128_ECB_encrypt_reference`. (Three of `aes_reference.c`'s four exports — the CBC pair and ECB decrypt — have no caller at this pin; that is upstream's internal dead code inside a single vendored TU that must stay whole. Not a Launchstation finding.) **Strike `aes_reference.c` from -072's deletion list.**

**(c) `sync.c` (`ps2.yaml:349`) and `smb2-share-enum.c` (`ps2.yaml:344`) — intra-library references EXIST, all in client-only code; deletion still rests on `--gc-sections`.** `sync.c`'s `smb2_open`/`smb2_close` are called by `libsmb2.c`'s own `smb2_notify_change_async` (`lib/libsmb2.c:4408,4417`) — a client API nothing in the server calls (smbd's change-notify is the *server* handler in `smbd_fs.c`, a different path). `smb2-share-enum.c`'s sole reference in the entire compiled set is `sync.c`'s `smb2_share_enum_sync`. So the pair forms a closed client-only cluster: share-enum ← sync ← one dead-in-this-build client function in `libsmb2.c`. Dropping both lines is safe **iff** the linker's `--gc-sections` (present in the target's `ldflags`, READ in `ps2.yaml`) discards `smb2_notify_change_async`'s section before its undefined references matter — the normal GNU ld behaviour, but exactly the link test round 3 demanded and this VM still cannot run (no PS2 toolchain). Status: *probably* deletable, unproven; do not describe them as unreferenced — they are referenced, by dead code.

**(d) `smb2-data-security-descriptor.c` (`ps2.yaml:342`) and `smb2-data-reparse-point.c` (`ps2.yaml:343`) — same status as (c).** Round 3 established no *first-party* handler exercises them (still true). Intra-library references exist, all client-side: `smb2_decode_security_descriptor` from the client query-info reply path (`lib/smb2-cmd-query-info.c:723`, inside `smb2_process_query_info_variable`); `smb2_security_descriptor_size`/`smb2_encode_security_descriptor` from the client set-info request encoder (`lib/smb2-cmd-set-info.c:251,266`); `smb2_decode_reparse_data_buffer` from the client ioctl reply path (`lib/smb2-cmd-ioctl.c:420`); `smb2_decode_symlink_error_response` and `smb2_encode_reparse_data_buffer` from `lib/libsmb2.c:1576` (`symlink_error_target`) and `:3405` (`smb2_symlink_async`). The server dispatch never reaches any of them (smbd's handlers are invoked from `lib/libsmb2.c`'s server-handler block, `libsmb2.c:4432ff`, which calls only `server->handlers->*`). Deletion safety is again a `--gc-sections` question for the link test, not a source question.

**Net effect on -072's fix:** of the 7 lines, delete 2 now (`quic.c`, `smbdirect.c` — provably empty); 4 (`sync.c`, `smb2-share-enum.c`, `smb2-data-security-descriptor.c`, `smb2-data-reparse-point.c`) go only with the one smbd link test -072 already prescribed, and the expected failure mode if the GC assumption is wrong is a loud undefined-symbol error naming the exact line to restore; 1 (`aes_reference.c`) stays permanently. The benefit framing is unchanged (build/audit surface, not shipped bytes).

### Two further round-3 open questions, settled (no findings)

- **Query-directory length consistency (round 3 Still Unread #1): CONSISTENT by construction.** `query_directory_cmd` (`iop/smbd/smbd_fs.c:606-607`) hands the library `rep->output_buffer = (uint8_t *)ent; rep->output_buffer_length = n * PAD8(sizeof(ent[0]))`. The library encoder (`lib/smb2-cmd-query-directory.c`, `smb2_encode_query_directory_reply`) does **not** treat that number as an output byte count: in non-passthrough mode it saves it as `fslen`, walks the handler's array in strides of `PAD_TO_64BIT(sizeof(struct smb2_fileidbothdirectoryinformation))` for exactly n entries, and **recomputes** the true output length itself (`fs_size = PAD_TO_64BIT(fixed + fname_len)` per entry, `fixed = dir_entry_size(info_class)`, name length from its own UTF-16 conversion), allocating exactly the recomputed length. The handler's room budget (`DIR_ENTRY_ROOM(namelen) = PAD8(104 + 2*namelen)`, `smbd_fs.c:25`) matches the encoder's per-entry arithmetic for the one class served. The handler's number is an entry-count×stride encoding — fragile-looking, but precisely the contract the encoder implements. The coupling worth recording: if a future libsmb2 re-pin changed the encoder's stride or stopped recomputing, this breaks silently; that is an argument for a comment at `smbd_fs.c:607`, not for code.
- **`authorize_user`'s set-password pattern: verified exactly as `smbd_fs.c`'s comment implies.** The library extracts user/domain/workstation from the client's NTLMSSP authenticate message and calls `server->handlers->authorize_user` (`lib/ntlmssp.c:1395-1404`); smbd's handler rejects any username other than the configured one and installs the expected password via `smb2_set_password` (`iop/smbd/smbd_fs.c:252-262`); the library then refuses to proceed without a password (`ntlmssp.c:1405-1410`, with smbd's `allow_anonymous = 0` closing the anonymous branch at :1413-1420) and verifies the client's NTLMv2 NTProofStr against that password, with explicit bounds checks on the attacker-controlled response field first (`ntlmssp.c:1436-1443`). The comment's claim is the mechanism. No finding.
- **Wire-input → encoder length pass (Task 1's standing scope question):** the one place a handler-supplied length reaches an encoder unchecked is the patched raw query-info path (`lib/smb2-cmd-query-info.c`, `smb2_encode_query_info_reply`): for encoder-less classes the (patched) code copies `rep->output_buffer_length` bytes from `rep->output_buffer`. First-party side: `query_info_cmd` sets that pair to `&info` and a compile-time per-class constant (72/96 for the raw stat classes, `sizeof(...)` for structured ones; `iop/smbd/smbd_fs.c:760,813-814`), and `info.raw` is 96 bytes — the largest constant equals the buffer. Client input selects only the class, and unimplemented classes are refused before this point. No wire value reaches the length. No finding.

### LAUNCHSTATION-079 / Superblock geometry is copied into `MCDevInfo` with no validation, then used as divisors, loop bounds and buffer offsets / Category 6
- **Locations:** `iop/vmcman/src/main.c:1391-1393` (raw 0x150-byte copy from page 0 over the geometry prefix of `MCDevInfo`, after only the magic check at :1383-1386 and a version-digit check at :1388-1389 — both spot-checked at the pin); `main.c:1334-1354` (`mcman_setdevspec` computes sane derived values *before* the copy, which the copy then overwrites); local mount validator `iop/vmcman/src/mciomanx_backing.c:107-141` (checks only magic, cardtype, `pagesize` ∈ {512, 528} and total file size). Sinks: `main.c:3791-3792,3835` (division by `cluster_size >> 9` — 0 when the card sets `cluster_size` < 512; spot-checked verbatim); `main.c:1435,1439` (`%` and `/` by `clusters_per_block` inside `mcman_setdevinfos` itself); `main.c:3766-3768` (`pages_per_cluster` page reads into a 1,024-byte cache slot, `mcman_cachebuf` at `main.c:45`); `main.c:3419,3520-3524` (`pmce[16]` indexed by `cluster % clusters_per_block`); `main.c:52,3543,3553` (`mcman_pagedata[32]` indexed by page index up to `clusters_per_block * pages_per_cluster`); `main.c:1181,1186,1195-1215` (stack `eccbuf[32]` walked `(pagesize + 127) >> 7` times).
- **Problem:** `mcman_setdevinfos` overwrites geometry the driver had just derived from the card *spec* with the first 336 bytes of page 0 — data the card image itself supplies. A crafted or corrupted image can set `cluster_size` to 0/256 (divide-by-zero in `McReadDirEntry`, reached from `mcman_setdevinfos` at `main.c:1401`), `clusters_per_block` to 0 (divide-by-zero at :1435) or >16 (write past `pmce[16]`, read past `mcman_replacementcluster[16]` at :3738-3742), and `pages_per_cluster * pagesize` to ≫1024 (every cluster read overruns its 1 KB cache slot into neighbouring entries). Local-delta interaction (basis for filing in vendored code): for the **physical** target (delta D10, §Ledger) there is no other gate — the superblock is the first card-controlled data the driver trusts. For the **VMC** target (D1), the local mount validator exists precisely to validate geometry but validates only `pagesize` and the product `pages_per_cluster * clusters_per_card`; `blocksize`, `pages_per_cluster` alone, `clusters_per_block`, `cluster_size`, `FATentries_per_cluster`, alloc bounds and backup-block numbers pass through unchecked in both layers, and `mcman_setdevinfos` re-reads page 0 instead of consuming the validated copy.
- **Fix:** After the copy at `main.c:1393`, reject the card (`return sceMcResNoFormat`) unless the copied fields equal the values `mcman_setdevspec` just derived (`pages_per_cluster`, `cluster_size`, `FATentries_per_cluster`, `clusters_per_block`) and `backup_block1/2 < clusters_per_card / clusters_per_block`. One comparison block reusing values already computed — no new tables, no new state, and no second validator in the backing layer.
- **Benefit:** Closes the divide-by-zero, cache-slot overrun and `pmce[16]`/`pagedata[32]` over-index classes at the single point where card geometry enters the driver, for both build targets. **Effort:** S. **Risk:** Low–Med — a non-standard but legitimate card whose superblock extension fields disagree with its spec would now be rejected as unformatted; that disagreement is exactly what the current code cannot survive anyway. **Confidence:** High (READ) for the absent check and each sink's arithmetic; INFERRED for on-hardware trap/overflow behaviour.

### LAUNCHSTATION-080 / `McGetFATentry`/`McSetFATentry` index `ifc_list[ifc_index]` with an unbounded `fat_index` — and card FAT values feed the same path / Category 6
- **Locations:** `iop/vmcman/src/main.c:3905-3931` (`McGetFATentry`: `ifc_index = (fat_index / FATentries_per_cluster) / FATentries_per_cluster` at :3911-3915, then `mcdi->ifc_list[ifc_index]` at :3917); `main.c:3872-3902` (`McSetFATentry`, same arithmetic at :3880-3886); `ifc_list` is `u32[32]` inside `MCDevInfo` (`iop/vmcman/src/mcman-internal.h:335`). Card-fed callers: `main.c:3813-3828` (`McReadDirEntry` walks `clust = McGetFATentry(..., clust, &clust)` where `clust` is the previous FAT entry masked only with `& ~0x80000000`); `main.c:1597-1643` (`mcman_fatRseek`, same pattern).
- **Problem:** Neither export checks `fat_index` against the card's FAT size. The index is (a) a direct argument of two library exports in the physical build (delta D10; `_dummy` in the vmcman build, `exports.tab:66,68`), and (b) derived from card-supplied FAT/dir data on internal walks: a FAT entry of 0x01000000 yields `ifc_index` = 4096 — a read ~16 KB past the array, across the rest of `MCDevInfo` and the following globals — whose value is then used as a cluster number for `McReadCluster`. `McSetFATentry` is the write-side twin: the OOB-derived cluster is read, modified, and marked dirty for flush. The only existing guards nearby are negative-only tests, which say nothing about large positive values.
- **Fix:** One guard at the top of each export: `if ((u32)fat_index >= mcdi->max_allocatable_clusters) return sceMcResNoEntry;`. Internal callers already handle FAT-walk errors.
- **Benefit:** Removes an OOB read (and a dirty-cache write primitive) reachable from a crafted card image's FAT chain alone. **Effort:** XS. **Risk:** Low — legitimate FAT indices are by construction below the allocatable-cluster count. **Confidence:** High (READ); INFERRED for what the OOB read lands on in a given build layout.

### LAUNCHSTATION-081 / Card-supplied entry names are still passed to `strlen`/`strcmp`/`strcpy` unterminated — the terminated-copy fix (delta D8) covered only the caller's copy / Category 6
- **Locations:** `iop/vmcman/src/main.c:2041-2055` (`mcman_getdirinfo`: `strlen(fse->name)` up to three times per entry, result used as the `strncmp` length — spot-checked verbatim); `main.c:1405,1411` (`strcmp(pfse->name, ".")` / `".."`); `main.c:2615` (PS1 20-byte name `strcmp`); `iop/vmcman/src/ps2mc_fio.c:283-284` (`mcman_dread2`: `strcpy(dirent->name, fse->name)` followed by `dirent->name[32] = 0` written *after* the unbounded copy — spot-checked verbatim). Contrast: the bounded pattern at `ps2mc_fio.c:1129-1132` and the D8 fix at `ps2mc_fio.c:383-390`.
