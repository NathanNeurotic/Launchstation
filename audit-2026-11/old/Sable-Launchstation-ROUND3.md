## Findings

### LAUNCHSTATION-053 / SMB READ/WRITE offsets are truncated to 32 bits before reaching the card / Category 6 (also 2)
- **Locations:** `iop/smbd/smbd.c:167-177` (`smbd_pread`/`smbd_pwrite`); callers in `iop/smbd/smbd_fs.c` (`read_cmd`/`write_cmd`) pass `req->offset` (a 64-bit SMB2 field) straight through.
- **Problem:** Both helpers do `iomanX_lseek(fd, (int)off, FIO_SEEK_SET)`. An authenticated remote client that sends offset `0x1_0000_0000` (or any value ≥ 2³¹) does not get an out-of-range error — the offset silently wraps (the `(int)` cast; ≥2³¹ also becomes a *negative* seek). A WRITE at 4 GiB therefore lands at offset 0 and overwrites the start of the file; a READ returns the wrong bytes. Memory cards are far smaller than 2 GiB, so **every** legitimate offset fits in a signed 32-bit seek — which means every offset that truncates is by definition bogus and should have been refused, not wrapped. **READ** (the cast, and that no range check exists in either handler); impact scenario INFERRED from SMB2 offset semantics.
- **Fix (LESS):** One guard, no new machinery: in `smbd_pread`/`smbd_pwrite`, `if (off > INT32_MAX) return -EINVAL;` before the cast — two lines total, in the platform file where the truncation lives.
- **Benefit:** A remote write can no longer be redirected onto live file data by offset arithmetic. **Effort:** XS. **Risk:** None for legitimate traffic (no PS2 memory-card file can be ≥2 GiB). **Confidence:** High (code READ; no hardware needed to validate the arithmetic).

### LAUNCHSTATION-054 / mmceman `SET_GAMEID`: unbounded `strcpy` into a 255-byte stack buffer, length pre-truncated through `u8` / Category 6
- **Locations:** `iop/mmceman/src/mmce_fs.c:1364-1366` (`char *str = (char*)arg; mmce_cmd_set_gameid(str)` — `arglen` ignored); `iop/mmceman/src/mmce_cmds.c:226-241` (`u8 len = strlen(ptr) + 1; u8 wrbuf[0xFF]; … strcpy(&wrbuf[0x4], ptr); mmce_sio2_tx_rx_pio(len + 5, …)`).
- **Problem:** The EE-supplied string is copied into `wrbuf[255]` at offset 4 with no length test: any string longer than 251 bytes overflows the stack buffer before the send length is even computed. The `u8 len` makes it worse, not better — for a 255+-byte string the declared wire length wraps while the copy does not. The one in-tree caller is safe by construction (`src/neutrino_gameid.c:248` passes a validated ID of exactly `NEUTRINO_GAME_ID_SIZE` = 12 bytes incl. NUL, `include/neutrino_gameid.h:6`, READ) — but the IOP handler enforces nothing itself.
- **Fix (LESS):** One guard at the top of `mmce_cmd_set_gameid`: `size_t len = strlen(ptr) + 1; if (len > 0xFF - 4) return -1;` (and widen `len` off `u8`). Deletes both the overflow and the wrap in a single check.
- **Benefit:** Closes a stack overflow at a devctl entry point. **Effort:** XS. **Risk:** None for the real caller (12-byte IDs). **Confidence:** High (READ).

### LAUNCHSTATION-055 / mmceman `GET_GAMEID`: unbounded `strcpy` of a firmware-supplied string into the caller's buffer, whose length the handler never receives / Category 6
- **Locations:** `iop/mmceman/src/mmce_fs.c:1360-1361` (`res = mmce_cmd_get_gameid(buf);` — `buflen` not passed); `iop/mmceman/src/mmce_cmds.c:195-216` (`rdbuf[0xFF]` fixed 255-byte packet; `char *str = &rdbuf[0x4]; strcpy(ptr, str);`).
- **Problem:** The game ID is copied out of the card firmware's reply packet with `strcpy`. Nothing guarantees the firmware's string is NUL-terminated within the 251 bytes available after the 4-byte header: a malformed/malicious/compromised MMCE device (the string's source is removable hardware) that returns 251 non-NUL bytes makes `strcpy` read past the stack `rdbuf` and write past the EE caller's `buf` — whose size the IOP side cannot even check, because the devctl wrapper discards `buflen` instead of passing it. No in-tree EE caller for `GET_GAMEID` was found (grep, READ) — the only in-tree game-ID flow is `SET_GAMEID` — so this is a latent trap armed for the first caller who allocates a "reasonable" small buffer.
- **Fix (LESS):** Bound the copy by both ends: pass `buflen` through (one parameter), copy with a bound of `min(buflen-1, sizeof(rdbuf)-4)` and force termination — or, smaller still and matching the protocol's fixed packet, reject a reply whose bytes `[4..254]` contain no NUL. Either is a few lines in one function.
- **Benefit:** Removable-hardware input stops being a memory-corruption primitive. **Effort:** S. **Risk:** A firmware returning an unterminated ID now gets an error instead of a corrupt copy — strictly better. **Confidence:** High on the unbounded copy (READ); device-malice scenario INFERRED (accidental unterminated replies suffice — malice is not required).

### LAUNCHSTATION-056 / smbman's `FileTimeToDate` computes wrong calendar dates — and it is the third, divergent copy of a conversion the other two drivers do correctly / Category 6 / 2
- **Locations:** `iop/smbman/smb_fio.c:563-615` (`FileTimeToDate`), called only by `smb_statFiller` at `smb_fio.c:617-627`. Correct counterparts: `iop/smb2man/smb2man.c:1015-1046` (`smb2man_pack_time`) and `iop/nfsman/nfsman.c:849-879` (`nfsman_pack_time`) — both use Howard Hinnant's `civil_from_days`; smb2man's even takes the same FILETIME input.
- **Problem:** The hand-rolled algorithm (divide by 365, subtract a leap-day estimate, then walk months with a strict `days > daysPerMonth[i]` test at `smb_fio.c:588`) is wrong on ordinary dates. Verified by executing a C-width-faithful Python replication of `smb_fio.c:563-615` this round: **80 of 240 sampled timestamps (1995–2034, six days per year) convert incorrectly** — e.g. 1995-03-01 → "1995-02-29" (a date that does not exist), 2000-03-01 → "2000-02-30", 1995-12-31 → day 146 of January 1997 (day and year both wrong). (READ for the code; the replication is host-arithmetic evidence, not a console test.) Every `smb1:` stat/dirent timestamp passes through this function. Secondary discrepancy in the same filler (READ): `smb_fio.c:621` maps `info->Change` to `stat->mtime` and never reads `info->LastWrite` (`iop/smbman/smb.h:298`), while `smb2man_fill_stat` (`smb2man.c:1059-1071`) uses the write time for `mtime` — the same file shows different modification times via `smb:` and `smb1:` (INFERRED impact: only the displayed/sorted mtime differs).
- **Fix:** Delete `FileTimeToDate`'s algorithm and use the in-tree Hinnant conversion the other two drivers already carry (`smb2man_pack_time` is a drop-in: same FILETIME input, same 8-byte output layout); take `mtime` from `LastWrite` while there. This is deletion-and-adoption, not a fourth implementation.
- **Benefit:** Correct dates from the SMB1 driver; one conversion algorithm left in the tree to maintain. **Effort:** S. **Risk:** Low (the replacement is already exercised by two drivers). **Confidence:** High for the wrongness (executed replication); High (READ) for the duplication.

### LAUNCHSTATION-057 / mmceman devctl dereferences `arg` as `u32` with no NULL/arglen check — in the same switch that already contains the correct pattern / Category 6
- **Locations:** `iop/mmceman/src/mmce_fs.c:1340-1341` (`MMCE_CMD_SET_CARD`), `:1353-1354` (`MMCE_CMD_SET_CHANNEL`), `:1394-1395` (`MMCE_SETTINGS_ACK_WAIT_CYCLES`), `:1399-1400` (`MMCE_SETTINGS_SET_ALARMS`) — all `args = *(u32*)arg;` — vs `:1377-1392` (`MMCE_CMD_SET_CARD_CHANNEL`), which checks `arg == NULL || arglen < 5` and reads bytes individually.
- **Problem:** Four devctl commands read four bytes through `arg` unconditionally. A devctl issued with `arg == NULL` or `arglen < 4` (any EE-side caller bug, or any future caller that treats these like the no-arg commands around them — `PING`/`GET_STATUS` in the same switch take no arg at all) dereferences a null/wild pointer on the IOP. The file itself proves the guard is the house style: the newest command in the same function has it; the older four never got it.
- **Fix (LESS):** Apply the sibling's existing check to the four cases — one shared `if (arg == NULL || arglen < 4) { res = -1; break; }` shape, copied, not abstracted.
- **Benefit:** One malformed devctl stops being an IOP crash. **Effort:** XS. **Risk:** None — in-tree EE callers pass a real `u32`. **Confidence:** High (READ; the contrast with `:1377` is in the same function).

### LAUNCHSTATION-058 / `smb_closeAll` sends server CLOSE for directory search handles and frees no handle slots at logoff / Category 6
- **Locations:** `iop/smbman/smb_fio.c:407-418` (`smb_closeAll`); callers `smb_fio.c:977` (`smb_LogOff`) and `smb_fio.c:1087` (`smb_CloseShare`). Contrast `smb_close` at `smb_fio.c:391-399`, whose comment and guard exist precisely to handle this correctly.
- **Problem:** Two defects, both READ. (1) `smb_closeAll` calls `smb_Close` for every slot with `smb_fid != -1`, with no `O_DIROPEN` exclusion — but a directory handle's `smb_fid` is a *search ID*, assigned from `info->SID` at `smb_fio.c:725`, not a file FID; `smb_close` guards against exactly this (`fh->mode != O_DIROPEN`, :394). (2) Unlike `smb_close` (:397-399), `smb_closeAll` clears nothing — no `memset`, `fh->f` and `f->privdata` survive — so after a logoff/close-share the 32 slots stay "open" holding FIDs of a torn-down tree. After a later logon, `smb_read`'s only validity test is `fh->smb_fid == -1` (:432), so a stale handle addresses whichever file the *new* session happens to give the same FID (INFERRED impact; the slot leak and the SID-close are READ).
- **Fix:** Make `smb_closeAll` reuse `smb_close`'s predicate and slot-clearing (both already in this file): skip `O_DIROPEN` handles' server close, and `memset` each slot / clear `privdata` exactly as :397-399 does.
- **Benefit:** Logoff stops issuing bogus CLOSEs and stops leaking the handle table across sessions; one definition of "end a handle" in the file. **Effort:** S. **Risk:** Low. **Confidence:** High (READ) for the mechanism; Medium (INFERRED) for the cross-session FID-aliasing harm.

### LAUNCHSTATION-059 / smbman's `lseek64` ignores the SEEK_END offset, accepts negative positions, and the 32-bit `lseek` truncates positions past 2 GiB / Category 6
- **Locations:** `iop/smbman/smb_fio.c:869-905` (`smb_lseek64`), `smb_fio.c:421-424` (`smb_lseek`). Correct counterparts: `smb2man.c:955-1010` and `nfsman.c:790-844` — both compute `base + offset`, reject a negative result, and make the 32-bit wrapper return `-EOVERFLOW` above 2 GiB (`smb2man.c:1004-1009`, `nfsman.c:838-843`).
- **Problem:** Three divergences, all READ: (1) `SEEK_END` at `smb_fio.c:891-893` sets `r = fh->filesize` and discards `pos` entirely, so `lseek(fd, -4096, SEEK_END)` — the standard tail-read idiom — lands at end-of-file on `smb1:` and at filesize−4096 on the other two drivers. (2) `SEEK_SET` (:884-890) and `SEEK_CUR` (:877-883) test only the upper bound, so a negative result is stored into `fh->position` (:899) and the next read/write hands a negative `s64` offset to the SMB wire fields (INFERRED wire effect from `iop/smbman/smb.c:1193-1194`'s u32 split). (3) `smb_lseek` (:421-424) casts the `s64` result to `int` with no overflow guard; positions up to `filesize` are legal in this driver, and `filesize` is a server-supplied `s64`, so a >2 GiB file seek truncates to a negative "error-looking" value.
- **Fix:** Adopt the siblings' seek body: `base + offset`, reject `< 0`, and the `-EOVERFLOW` guard in the 32-bit wrapper. Deletion of divergence, no new logic.
- **Benefit:** `smb1:` seeks behave identically to `smb:`/`nfs:`; tail reads work; large-file seeks stop lying. **Effort:** S. **Risk:** Low. **Confidence:** High (READ).

### LAUNCHSTATION-060 / smbman's read/write/dread/lseek dereference the handle without the validation its own close performs — and neither read nor write rejects a negative size / Category 6
- **Locations:** The validation that exists: `iop/smbman/smb_fio.c:386-387` (`smb_close`: `fh == NULL || fh->f != f` → `-EBADF`). The unguarded dereferences: `smb_read` `smb_fio.c:429-436`, `smb_write` `smb_fio.c:453-459`, `smb_dread` `smb_fio.c:696,711`, `smb_lseek64` `smb_fio.c:872-878`. Missing size checks: `smb_fio.c:435-440` and `smb_fio.c:464`, vs both sibling drivers' explicit `if (size < 0) return -EINVAL;` (`smb2man.c:874,915`; `nfsman.c:701,741`) and their generation-checked slot lookup on every op (`smb2man.c:751-763,828-839`; `nfsman.c:570-579,661-677`).
- **Problem:** `smb_read` dereferences `fh` in its first test (`fh->smb_fid`, :432) and computes the clamped size from `fh->position`/`fh->filesize` *before* taking the IO lock (:435-438), while `smb_close` frees and `memset`s that same handle under the lock (:389-401) — a stale or NULL `privdata` that `smb_close` would have rejected is a wild dereference here. If `position > filesize` ever holds, :436 computes a negative `size` and passes it to `smb_ReadFile`, whose loop simply returns the negative count as its result (`iop/smbman/smb.c:1155-1172`) — a nonsense pseudo-error instead of `-EINVAL`. Triggerability depends on ioman/EE caller behaviour (INFERRED); the asymmetry itself is READ and total: of the three network drivers in this tree, only the SMB1 one trusts `privdata` blindly.
- **Fix:** Give `smb_read`/`smb_write`/`smb_dread`/`smb_lseek64` the same two-line guard `smb_close` already has, move the size clamp inside the lock, and add the siblings' `size < 0` rejection. No new helper needed — the pattern is already in the file.
- **Benefit:** A stale handle on `smb1:` returns `-EBADF` like everywhere else instead of dereferencing freed state on the IOP. **Effort:** S. **Risk:** Low. **Confidence:** High (READ) for the missing checks; Medium for practical triggerability (INFERRED).

### LAUNCHSTATION-061 / `SMBD_DEVCTL_START` can read past the caller's argument buffer for the password / Category 6
- **Locations:** `iop/smbd/smbd.c:278-289` (`dev_devctl`, case `SMBD_DEVCTL_START`).
- **Problem:** Validation is only `arglen > 2 && ((char *)arg)[arglen - 1] == '\0'`. The code then does `strncpy(password, (char *)arg + strlen(arg) + 1, …)`. For a well-formed `"USER\0PASSWORD\0"` that is fine, and the one in-tree EE caller always sends exactly that (`src/init.c:2790-2793`, READ). But an arg consisting of a **single** string (`"USER\0"`, arglen 5) passes both checks, and `strlen(arg)+1 == arglen`, so the password `strncpy` starts reading **one byte past the caller's buffer** and keeps reading IOP memory until it happens on a NUL or exhausts 31 bytes — installing heap/stack residue as the server password. There is no check that a second string actually exists inside `arglen`. (The `user` copy itself is bounded by `strncpy(…, sizeof(user)-1)`; the stale-byte-31 concern is neutralised today because byte 31 is never written by either copy site — noted, not counted.)
- **Fix (LESS):** Add the missing existence check to the existing condition — `strlen(arg) + 1 < arglen` — one clause, no new code paths.
- **Benefit:** Closes an out-of-bounds read at the module's only credential-taking entry point. **Effort:** XS. **Risk:** None; the in-tree caller is well-formed. **Confidence:** High on the code path (READ); memory consequence INFERRED (IOP has no MMU isolation between modules, so the realistic outcome is a garbage password, not a fault). *The credential values involved are not reproduced anywhere in this report.*

### LAUNCHSTATION-062 / `DMA_sendEE` spins forever with no timeout, called with the SMB IO lock held / Category 5
- **Locations:** `iop/smbman/smb_fio.c:908-926`; sole call site `smb_fio.c:1037` inside `smb_GetShareList`, reached from `smb_devctl` (`smb_fio.c:1140-1142`), which holds `smb_io_lock` for the whole dispatch (`smb_fio.c:1123-1164`).
- **Problem:** Two unbounded loops: `while (!id)` retrying `sceSifSetDma` (:919-923) and the pure spin `while (sceSifDmaStat(id) >= 0);` (:924-925) — no timeout, no yield, no error path; the function returns `void`, so the caller cannot learn of failure. If the DMA never completes (a bad `EE_addr` in the devctl argument is INFERRED as one route; an EE-side stall is another), the `smb1:` device wedges with the IO semaphore held, which also starves the keepalive thread waiting on the same semaphore (`smb_fio.c:182-219`). Both newer drivers bound every wait (`smb2man.c:90-145`, `nfsman.c:79-124`); this is the one unbounded wait left among the four files read in Task 2.
- **Fix:** Bound both loops with a retry budget and return an error, propagating it through `smb_GetShareList` (its only caller chain already returns `int`). Behaviour on success is unchanged.
- **Benefit:** A failed share-list DMA becomes an error return instead of a permanently hung network device. **Effort:** M (signature change from `void` to `int`, one call site). **Risk:** Low. **Confidence:** High (READ) for the unbounded loops; INFERRED for the hang scenario.

### LAUNCHSTATION-063 / smbman's `dread` copies a server-supplied directory name with a `strncpy` that can leave `dirent->name` unterminated / Category 6
- **Locations:** `iop/smbman/smb_fio.c:751` (`strncpy(dirent->name, info->FileName, SMB_NAME_MAX)`; `SMB_NAME_MAX 256` at `smb_fio.c:77`). The source is a flexible-array member fed from the server reply (`iop/smbman/smb.h:312-320`: the search buffer explicitly accommodates names up to ~3.8 KB). Safe counterparts in the same audit set: `nfsman.c:1020-1021` (copy at size−1 plus a forced NUL) and `smb2man.c:1289` via `smb2man_name_utf8` (always NUL-terminates within `outmax`).
- **Problem:** `dirent` is zeroed at `smb_fio.c:704`, so termination survives only while the name is shorter than 256 bytes. A server returning a name of ≥256 bytes — permitted by this driver's own search-buffer sizing — makes `strncpy` fill every byte of `dirent->name` with no NUL, and EE consumers treat that field as a C string (e.g. the `strcmp` filters in `src/filer.c`). A compromised or merely long-name-serving SMB1 server is within the threat model these drivers were hardened against in round 2.
- **Fix:** Copy the nfsman way, two lines at the same site: bound at `sizeof(dirent->name) - 1` and write the final NUL explicitly.
- **Benefit:** Every `smb1:` directory entry is a valid C string by construction, like the other two drivers'. **Effort:** S. **Risk:** Low. **Confidence:** High (READ) for the pattern; trigger requires a ≥256-byte server filename (INFERRED reachability — unusual for SMB1 long names, but the buffer design admits it).

### LAUNCHSTATION-064 / smbd's replacement `calloc`/`malloc` do not check size arithmetic / Category 6 / 5
- **Locations:** `iop/smbd/smbd.c:38-66` (`malloc`: `AllocSysMemory(ALLOC_FIRST, size + 8, NULL)` with `int size`; `calloc`: `malloc(n * size)` then `memset(p, 0, n * size)`).
- **Problem:** These functions replace the allocator for the **entire IRX, libsmb2 included**, i.e. for allocations whose sizes are influenced by remote PDU length fields. Neither checks its arithmetic: `size + 8` wraps for `size` near `INT_MAX`, and `calloc`'s `n * size` (computed in `size_t`, then narrowed into `malloc`'s `int` parameter) can wrap to a small allocation that the subsequent `memset(p, 0, n * size)` — recomputed at full `size_t` width — then overruns. Whether a remote-reachable libsmb2 call site actually feeds attacker-sized `n`/`size` into `calloc` is **INFERRED** (libsmb2 absent); the defect in the local code is READ.
- **Fix (LESS):** Two guards in one place: in `calloc`, `if (size && n > SIZE_MAX/size) return NULL;`; in `malloc`, reject `size < 0 || size > INT_MAX-8` (or type the parameter `size_t` and check once). ~3 lines, no new abstractions.
- **Benefit:** The single choke point for all server allocations stops being an overflow amplifier. **Effort:** XS. **Risk:** A wrapped request now returns NULL, which libsmb2 already handles (every handler in `smbd_fs.c` checks allocation failure). **Confidence:** Medium (local defect READ; remote reachability INFERRED).

### LAUNCHSTATION-065 / `write_cmd` never caps the transfer length; `read_cmd` does / Category 6 / 2
- **Locations:** `iop/smbd/smbd_fs.c` `read_cmd` (caps: `if (len > SMBD_MAX_IO) len = SMBD_MAX_IO;`) vs `write_cmd` (no cap; `smbd_pwrite(card_fd, req->buf, (int)req->length, req->offset)`).

### R3-R3 — New evidence on LAUNCHSTATION-051 (`prepare_path`, `iop/smbman/smb_fio.c:305-334`) — narrows it in one direction, strengthens it in another; NOT a new finding
- **Narrowing (against the worst reading of -051):** once the `strcat` at :312 survives, the output *is* terminated by construction, twice over. The copy loop's condition is `p <= p2` (:325) where `p2` points **at** the source string's terminating NUL (:320), so the NUL is copied into `full_path` as data; :330-331 then write a backslash and a second NUL after it, and the loop guard (`max_path - i - 2 > 0`) keeps those two writes in bounds. The -051 hazard is therefore confined to exactly the :311-312 idiom: if `smb_curdir` ever reaches length ≥ `max_path - 3` unterminated, `strncpy` leaves no NUL and the `strcat` walks off — the input side, not the output side.
- **Strengthening (new defect inside the same function):** the trailing-slash strip at :320-322 is dead code that can never execute — `p2` is initialised to `&path[strlen(path)]`, i.e. at the NUL terminator, and NUL is neither `'\\'` nor `'/'`, so the `while` body never runs. Consequently `prepare_path` never strips trailing slashes and never actually appends the trailing backslash its comments (:319, :329) describe — the :330 backslash lands after the embedded NUL, invisible to every C-string consumer. Callers compensate inconsistently (e.g. `smb_dopen` re-derives the last visible character itself at `smb_fio.c:659,673`). This is comment/code divergence plus a dead loop in the very function -051 flagged, and it means any future fix to -051 should rewrite the tail handling, not just add the one terminating line.

## Checked in round 3 and deliberately NOT flagged

### smbd (Task 1)
- **Path traversal (READ, clean):** `make_path` (`smbd_fs.c`) rejects `..` components and any component containing `:`, skips `.`/empty components, strips leading separators, and checks `n + 1 + len >= SMBD_PATH_MAX` **before** each `memcpy`. A request cannot leave its share root by construction.
- **Tree connect (READ, clean):** `tree_connect_cmd` truncates the share name into `char name[8]`, but acceptance requires `len == 3 && ieq(name, share_names[i])` on the **untruncated** length — truncation cannot be used to alias a longer name onto `mc0`/`mc1`.
- **Rename (READ, clean):** `rename_handle` validates `buffer_length ≥ 20`, `FileNameLength ≤ len-20` and even, allocates `n+2` before `memcpy`; refuses root renames, cross-folder renames (same-prefix + leaf-only via `SMBD_LEAF_MAX` check), in-use targets, and non-empty semantics; the `SMBD-OLD.TMP` aside-buffer arithmetic `(b - to) + sizeof("/SMBD-OLD.TMP") > sizeof(aside)` is exact (allows exactly 128 including NUL). `smbd_rename`'s `strcpy(info.EntryName, leaf)` (`smbd.c:216`) is safe because the leaf is pre-checked ≤31 and `EntryName` is `char[32]` (`iop/vmcman/include/mcman.h:32`, READ).
- **Set-info lengths (READ, clean):** disposition checks `buffer_length < 1`; end-of-file checks `< 8`; both before dereferencing `buf`.
- **Query-info raw classes (READ, clean):** fixed-size raw classes are refused with `STATUS_INFO_LENGTH_MISMATCH` when `output_buffer_length` is too small, rather than truncated.
- **Handle table (READ, clean):** `lookup` validates index, `used`, **owner == requesting context**, and generation — one client cannot address another's handle, including via the all-ones compound-request id (the `last_create` shortcut still passes through the owner check).
- **Write-on-read-only-handle (dissolved, READ+INFERRED):** `write_cmd` does not itself test `handles[i].write`, but the single cached card fd is (re)opened by `card_fd_of` with exactly that handle's write flag, so a read-only handle's fd is `FIO_O_RDONLY` and the write fails at the iomanX/MCMAN layer. Defence exists, one layer down.
- **Auth surface (READ, clean apart from LAUNCHSTATION-067):** no anonymous/guest (`allow_anonymous = 0`), signing enabled, username equality is case-insensitive but length-exact in effect (`ieq` returns true only when both strings end together — walked through prefix cases), `SMBD_MAX_CLIENTS 2` enforced in `on_new_client` with the `destruction_event` decrement matching the refused-client path by design (commented in code).
