Install & Update

Install the matching app package, keep your configuration and customized files, and update in place only from a release that can be verified.

Standard rolling package

mc0:/
└── APP_LAUNCHSTATION/
    ├── LAUNCHSTATION.ELF
    ├── title.cfg
    ├── BGM.ADP
    └── WLE-UPDATE-CA.PEM

Both the standard ZIP and PSU contain those four files, and the executable is packed (ps2pack). DS34 controller packages use APP_LAUNCHSTATION-DS with LAUNCHSTATION-DS.ELF and the same three sidecars. The ELF alone runs the dashboard. WLE-UPDATE-CA.PEM is the trust root for HTTPS update checks, BGM.ADP is optional background music, and title.cfg is an OPL-style application descriptor.

The full kit (LAUNCHSTATION-<build>.zip)

mass:/
├── APPS/APP_LAUNCHSTATION/      the standard app (same four files)
├── APP_LAUNCHSTATION.psu        the same app as a memory-card save
├── POPS/                        POPStarter, its companions and the BDM Assault driver pairs
├── EMBER/                       Ember (ember.elf, licence, games/ layout; add your own bios.bin)
├── neutrino/                    the latest upstream Neutrino release
├── *.url                        PS2-Servers, Android UDPFS server, OPL PS1 AIO converter, OrbitPS2 Manager, this site
├── KIT-README.txt               what each folder is for and who made it
└── KIT-MANIFEST.json            build number, source commits and the SHA-256 of every file

The kit has the same layout as RiptOPL’s release ZIP, so one copy to the root of a game device gives Launchstation the external loaders it hands games to: VCDs start through <device>:/POPS/POPSTARTER.ELF (POPStarter), .CUE/.BIN/.EXE images through the Ember directory you point at EMBER/, and PS2 ISOs through <device>:/neutrino/neutrino.elf (Neutrino; whether that build carries the SMB modules is recorded in KIT-MANIFEST.json, since upstream’s latest archive does not always include them). POPS/ and EMBER/ are the files RiptOPL ships, pinned to one RiptOPL commit (ship/kit-externals.json) and checked byte for byte; neutrino/ is the ps2max32/neutrino latest release downloaded when the kit was built, and KIT-MANIFEST.json records both. The kit holds only the standard controller build; the DS34 build stays in APP_LAUNCHSTATION-DS. No PlayStation BIOS or game is included, and the in-app updater keeps downloading the PSU, not the kit.

Choose your installer

Download the matching ZIP/PSU from Downloads & Releases. Extract the ZIP app folder to readable storage, or copy the PSU in the File Browser and choose Extract PSU inside a memory-card folder. Keep a separate copy of your previous working ELF, settings and customized sidecars.

Where it can run from

Launchstation can be started from any device your launcher can boot an ELF from. The in-app updater can replace the running ELF in place when it was started from a mc, mass/usb, mmce, mx4sio, ilink, ata or hdd path; other boot locations get an explanation and are left unchanged. Unit numbers are not restricted, because USB numbering depends on attach order.

Configuration

LAUNCHSTATION retains classic LAUNCHELF.CNF support and its dashboard settings store (DASHBOARD.CNF). The saved path can be configured next to the ELF, in a selected folder or on a memory-card SYS-CONF location (Settings > System > Configuration folder). See Configuration.

Google Drive remains opt-in

Official builds embed Launchstation's own OAuth client, so linking needs no setup files: choose Link Google Drive and enter the shown code at google.com/device. Launchstation then stores a refresh token in WLE-CLOUD.TOK. Do not publish your token or include it in a bug report. Google Drive is optional for ordinary files and local MMCE history. A build you compile yourself has no embedded client unless you supply one; see developer notes.

Native updates and rollback

Open Settings > Storage & devices > MMCE backups > Check for updates. It needs a configured wired network (Settings > Network) and WLE-UPDATE-CA.PEM beside the running ELF (or in the dashboard settings folder). The updater then:

  1. Reads the rolling latest release from GitHub and the SHA-256 digest GitHub publishes for the package that matches your variant (standard or DS).
  2. Asks GitHub to compare your build's commit with the release commit. It continues only when the release is a verified descendant (newer). Identical or older builds report "no newer release"; a divergent history, a local/unrecognized build or an unverifiable comparison blocks automatic replacement and tells you to install a complete package manually.
  3. On your confirmation, downloads the PSU over HTTPS, checks the SHA-256, extracts the ELF into a .UPDATE file and validates it as a PS2 ELF.
  4. If the four-file PSU contains a WLE-UPDATE-CA.PEM or BGM.ADP that is missing beside the app, stages and adds it. Existing sidecars, including a custom BGM, are never overwritten.
  5. Renames the running ELF to <name>.ELF.BAK (replacing an older .BAK) and renames the verified file into place; if that final step fails it restores the original.

The running session keeps the old code. Restart Launchstation to use the new build. To roll back, rename LAUNCHSTATION.ELF.BAK (or the DS equivalent) over the ELF with the File Browser. If an .UPDATE or .PACKAGE file from an interrupted attempt exists, the updater refuses to touch it and changes nothing: inspect it, recover what you need and delete it manually before retrying.

Older builds
Updaters shipped before the four-file packages expect standalone ELFs or two-file PSUs and cannot install the current PSU automatically. Install the matching complete ZIP/PSU manually once (keeping your settings); in-app updates work from then on. A legacy two-file PSU update replaces only the ELF.

Manual update or downgrade

  1. Copy your current settings (LAUNCHELF.CNF, DASHBOARD.CNF) and the working ELF somewhere safe.
  2. Extract the new ZIP over the app folder, or install the PSU on a memory card. Do not overwrite a customized BGM.ADP unless you want the stock music.
  3. Start the new ELF and check the commit in Tools > About Launchstation.

Building from source

Release packages are built by CI from master with the PS2BUILD LLVM/Clang toolchain. To build your own, follow the repository README and the developer notes; builds you compile yourself need the embedded Google client variables (see above) for zero-setup Drive linking.

Preserve a hardware-tested baseline

If a newer rolling build regresses on your console, retain the 2026-10-08 USB-tested baseline and collect hardware details before retrying. Compiled CI success is distinct from successful console validation.
