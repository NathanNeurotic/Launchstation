Device Support

Launchstation treats every storage type as its own device with its own driver stack. Drivers load on demand, so a device card tells you whether Launchstation has checked that device, not merely whether a driver exists. This page is the overview; the per-device pages explain each type in depth.

Where devices appear

Open the Files tab. The default view lists File Browser, Last folder, MISC commands and your bookmarks; the File Browser’s root list shows every device the build supports. Press SELECT to switch to the device cards, which show a status line, free space where known, and a coloured status light. Press Triangle on a card for Browse, Detect now / Check again, HDD Manager (internal HDD card), Start disc (disc drive card) and Console information.

Device states: Ready, Not checked, Absent, Busy

A demand-loaded driver cannot know whether hardware is attached until it runs, so Launchstation does not guess.

  • Ready – an explicit check succeeded (or the device is the one Launchstation booted from) and its driver is running.
  • Not checked – shown dimmed with the status Not connected. This is not a failure: select it and confirm and Launchstation loads the driver and probes the device. The hint line reads “opening it will load its driver”.
  • Absent – a check ran and found nothing (Slot empty, No MMCE storage found, Connect a USB storage device…). Absent cards are displayed but skipped by focus navigation in the device cards. To try again after connecting hardware, open the device from the File Browser root list (which re-runs its lazy loader).
  • Busy – a memory card that is still being checked or did not answer (Checking…, Not responding – open to retry). Opening it retries.

A loaded driver does not prove media is present: driver residency never makes a device Ready on its own. Check results are snapshots, expire after any IOP reset, and are not continuous hot-plug monitoring; use Check again after you attach or remove something. Cached applications on a device that failed its check are hidden from Home until it is Ready again.

Start devices automatically

Settings > Storage & devices > Start devices automatically has one switch per family: USB, internal HDD, exFAT HDD, MMCE, MX4SIO, iLink (when the console has the port) and network (UDPFS). All default to off, so a stock boot loads nothing beyond the memory-card services and whatever device the ELF was started from; that boot device is always treated as enabled. Auto-start runs while the loading screen is up, and the application library is refreshed afterward.

MMCE and MX4SIO are mutually exclusive (they both use the memory-card port SIO2 bus). Turning one on turns the other off, and Launchstation refuses to enable one while you are booted from the other. See Stacks that cannot coexist.

Hiding and showing devices

  • Show unavailable devices (default On) keeps Not checked and Absent families visible. Off lists only Ready devices and removes the others from both drawing and navigation, so the focus rectangle never lands on a hidden card.
  • Hide empty memory card slots also hides unused MMCE entries in the File Browser.
  • Internal HDD / ATA units chooses which of hdd0, hdd1, ata0, ata1 appear: Show all, Hide HDD1, Hide HDD0+1, Hide ATA1, Hide ATA0+1, Hide HDD1+ATA1 (default) or Hide all.
  • Console-based hiding. HDD and ATA are hidden automatically when the ROM version is 2.20 or newer (expansion-bay-less slim consoles). iLink is hidden on retail ROMs from 1.70 onward (SCPH-50000 and later removed the port); unknown or non-retail ROMs and the PSX keep it visible. xfrom0: and dvr_hdd0: appear only on a DESR PSX. PC CARD CF appears only on eligible early Japanese consoles. See PSX, Deckard & RetroGem.

Recovery boot: hold SELECT

Hold SELECT while Launchstation starts. This sets show every device (ignoring the Hide HDD/ATA choice and the console-model hiding for HDD/ATA, PSX flash/DVR and the PC CARD CF entry; iLink visibility is not overridden) and safe mode: DASHBOARD.CNF is skipped for that boot, so a saved auto-start combination cannot trap you, and PC CARD CF is shown as Disabled in safe mode (or Unsupported console model) and never powered. Saved settings are not changed. A toast confirms “Safe mode” on the dashboard.

Stacks that cannot coexist

  • MMCE ↔ MX4SIO. Each installs its own SIO2 hooks, so switching from one to the other forces an IOP reset (audio and controller are rebuilt afterward). If the reset is refused, the second driver is not loaded. MX4SIO also occupies memory-card port 2, so opening mc1: while MX4SIO is active resets the IOP back to the normal card stack.
  • PC CARD CF ↔ DEV9. The CF driver owns the PCMCIA bus and refuses to start if DEV9 (HDD, ATA, network) is resident; DEV9 loaders refuse in turn once CF owns the bus. Only an actual IOP reset releases it.
  • Compatible together: USB, iLink, internal HDD (APA) and exFAT HDD (ATA) can all be resident at once; they share the BDM core where applicable. Network (UDPFS) shares DEV9 with HDD/ATA.

Memory cards

Slots are always probed in the background and labelled by port (mc0 (Slot 1), mc1 (Slot 2)). The card shows PS2 memory card or PS1 memory card and free space in MB (against 8 MB for a PS2 card). They are the target for the exploit installer and the default location for saves. A memory card cannot hold game images, but mc0:/neutrino/ or mc1:/neutrino/ may hold a complete Neutrino install.

USB

USB uses the BDM stack with FAT/exFAT filesystems and up to ten logical units (MASS 0–MASS 9; each partition is its own unit). The browser shows massN: for what is internally usbN:, and numbering follows attach order – never assume mass0: is a particular stick, especially with MX4SIO or iLink attached (those also take massN: names from the shared namespace).

Enumeration and intermittent stalls

When the USB stack starts, Launchstation probes at most four times, 0.6 s apart, accepting a second drive that appears late. Each probe is a synchronous PS2 IOP filesystem call: the retry count is bounded, but one call that blocks inside the driver cannot be timed out from the EE. The controller’s analog light going out during a stall points to a stuck PAD/SIO2 or IOP session; it does not by itself prove a software reset. Two bus-powered drives can also overload the console’s USB supply. Compare behaviour with one drive, a powered hub, and an older build, and do not unplug a drive during writes. The project uses the pre-rewrite usbd host driver (usbd-ra) loaded before BDM because the newer ps2sdk driver was observed to lock the IOP on real consoles; see the USB stability audit, whose freeze report is not yet confirmed fixed on the reporter’s console.

Tools: USB unit diagnostics

Use Tools > USB unit diagnostics to inspect the last cached logical-unit mask without any new I/O, or explicitly probe USB unit 0 or 1 one at a time. A manual probe is a synchronous IOP call; a failing driver can still freeze the console. Logical usb0:/usb1: numbers are not physical port numbers.

Start disc boots PS2 discs through their SYSTEM.CNF boot file (writing the OSD history entry and applying the console’s XPARAM patches), PS1 discs through rom0:PS1DRV, DVD Video through the console’s own player (or an updated BREXEC-DVDPLAYER on a memory card), and ESR discs through the configured ESR loader. Audio CDs are not started.
