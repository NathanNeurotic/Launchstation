Architecture & Repository Layout

Where things live in the repository, how a build turns them into one PS2 ELF, and the runtime rules that keep the console stable.

Repository layout

How the build fits together

ps2.yaml declares IOP targets, EE libraries, the loader, the WLE-IGR helper and the main wLaunchELF target. IOP modules built here, SDK driver packages and the loader/IGR ELFs are listed under embed_irx: and become byte arrays inside the main ELF; plain files are embedded by src/embed_blobs.S. Feature flags (MMCE, MX4SIO, ETH, UDPFS, EXFAT, ILINK, DVRP, XFROM, DS34, WLE_NATIVE_CLOUD and others) are defines: on that target and gate code with #ifdef. The DualShock build is generated from the same file, so the two variants cannot drift. Everything is then packed with ps2pack and wrapped into the ZIP/PSU packages. Full commands are in Building from Source.

Runtime rules

  • One shell. main() performs early boot, input and display initialization, optional IGR backup, then calls DashRun(), which never returns. Settings, the File Browser, HDD Manager, Text Editor and exploit installer are dashboard screens.
  • Lazy drivers. Embedding a module only places it in the ELF; init.c decides when to load it, and each load_* function checks whether the stack is already resident. Nothing for USB, ATA/HDD, MMCE, MX4SIO, iLink, networking or controllers beyond the pad driver starts until a screen needs it.
  • Exclusive stacks. Some families cannot coexist (ETH versus UDPFS networking, MMCE versus MX4SIO on the same SIO2 bus, PS2 versus PSX HDD stacks, the PC CARD CF driver versus DEV9). Switching between them normally resets the IOP and clears residency tracking so the next access reloads what it needs (the PSX APA/DVR HDD stacks are the exception: they load without a reset). Neutrino quick-boot reuses the mounted stack; Ember's USB path performs a controlled clean rebuild first.
  • Background worker. One EE thread (dash_worker.c) runs queued file, memory-card and driver jobs at lower priority; while it runs the UI thread does no I/O of its own, jobs never draw or show dialogs, and completion callbacks run back on the UI thread. Anything that reboots the IOP or launches an ELF first drains the queue. Some USB and device probes are still synchronous IOP calls and can block on failing hardware.
  • Persistence. The dashboard never edits LAUNCHELF.CNF; it writes DASHBOARD.CNF, DASHAPPS.CNF and DASHLIB.CNF next to the loaded configuration or in mc0:/SYS-CONF/, with explicit Save/Discard semantics.
  • Safety first for backups. MMCE history is written to .PART files, verified and renamed; recovery produces new files and never overwrites an active card; direct restore stays disabled (research/sd2psxtd is a reference model only and is not linked into any ELF).

Refactoring status

The oversized legacy files have been split along behavior-neutral lines: main.c into main_actions, main_boot, main_modules, main_menu, main_info_screens, main_gameid and others; filer.c into filer_device, filer_mount, filer_fileops, filer_actions, filer_browser, filer_copy, gui_sort, gui_texteditor, gui_hdd0_format and psu_functions; PSU layout structs are shared via include/psu_types.h. The legacy SMB and classic JPG-viewer subsystems were removed; images are viewed by the dashboard's bounded PNG (dash_png.c) and JPEG (dash_jpeg.c, libjpeg-turbo) decoders. The largest hand-written files now are dash_settings.c, dash_browser.c, init.c, main_exploit_installer.c and filer_browser.c (make stale-audit lists the top ten). Keep each further split behavior-neutral and verify it in an emulator and on real hardware.
