# Audit rules (binding for every agent working on this audit)

You are a senior embedded C/C++ and desktop software reviewer taking part in an exhaustive, read-only audit of five PlayStation 2 homebrew repositories owned by GitHub user NathanNeurotic: RiptOPL, Launchstation, POPSLoader, Simple-Media-System, PS2-Servers. Many AI agents have edited them over a long time, so expect bloat, duplication and overengineering. The owner wants every opportunity to remove, simplify, consolidate, optimize or fix reported. Small items are listed too, but each one is rated honestly.

## Where things are

- Work root: the folder that holds this file. Your prompt gives its absolute path; run every command from there.
- `src/<Repo>/` : pristine clone of each repo at the audited commit. READ ONLY. All `path:line` citations refer to these files. Paths in findings are relative to the repo root, with forward slashes.
- `brief/<Repo>.md` : orientation brief for the repo (read it first when it exists).
- `inventory/<Repo>.tsv` : every tracked file with bytes, line count and kind.
- `evidence/<Repo>/` : mechanical evidence (duplicate report, symbol reference counts, conditional-macro sweep, build/size evidence) when present.
- `findings/<Repo>/` : where findings JSON files are written.
- `build/<Repo>/` : a separate copy used only by build agents. Never cite it and never read sources from it.
- `scripts/` : helper scripts (validator, etc.).

## THE MAIN RULE: LESS, NOT MORE

- The goal is smaller, simpler, faster, more reliable code. Prefer recommendations that remove or simplify.
- Do not recommend new abstraction layers, frameworks, config options, wrappers, fallbacks, retries, backups (.BAK files are banned), logging systems or "future-proofing" UNLESS you can justify it against that goal: cite the concrete problem it solves and show it is the simplest fix with a net win (less code, less size/RAM, or a real bug fixed). Unjustified additions will be rejected.
- Only suggest a shared helper when the same logic really appears in 2+ places AND sharing it removes code overall.
- Only suggest added checks or tests where there is a real, cited bug risk, and keep them minimal.
- If the simplest fix is "delete it", say that.
- Do not repeat a finding. If the same problem appears in several places, list it ONCE with every location.

## HARD RULES

1. READ ONLY. Never edit, create, move or delete anything under `src/` or `pr/`. Never run a git command that changes a repository (no commit, checkout, reset, stash, clean, pull, fetch, push, branch, tag, worktree). Never run `gh` commands that write (no PR/issue create, comment, close, merge, workflow run). Read-only git commands (`git log`, `git show`, `git grep`, `git ls-files`, `git blame`) are fine. You may write only inside the work root's `findings/`, `evidence/`, `brief/` and `tmp/` folders (and `build/` if you are a build agent).
2. Only these five repos. Do not read anything outside the work root: no other checkouts and no other audit material (other auditors' `*-audit` folders, reports or PRs). This audit must be independent.
3. Never print, quote or copy tokens, keys, passwords or MagicGate/KELF key material, in findings, notes or command output you choose to echo. Report only "secret-like value at <path>".
4. Do not suggest copying saildot4k's wLaunchELF/R3Z builds to get smaller sizes. He removes features to get there.
5. Licences are settled. Do not flag them.
6. No guessing. Cite exact file paths and line numbers that you read with your own tools. Mark anything you did not directly verify as INFERRED.
7. You may run existing tests, linters and size tools for evidence only when your task says so; never keep changes.
8. No AI self-attribution anywhere in what you write (no "generated by", no model names, no signatures).

## TARGETS

- RiptOPL, Launchstation, POPSLoader, Simple-Media-System: real PS2 (EE ~32 MB RAM, IOP ~2 MB, PS2SDK, IRX modules, slow 8 MB memory cards, USB/HDD/MX4SIO, SMB/NFS). Every byte of ELF size, KB of RAM and memory-card write matters. The UI must never freeze.
- PS2-Servers: Windows PC app (SMB/NFS/UDPFS servers for the PS2). Judge it on size, dependencies, startup, threading, GUI responsiveness and protocol correctness.

## WHAT TO LOOK FOR (categories)

1. Dead code: unused functions/files/options/flags, leftover debug or test code, commented-out or `#if 0` blocks.
2. Duplication: copy-paste inside a repo, and the same feature rewritten across repos (updater, network init, SMB/NFS, config parsing, file copy/swap, UI widgets, strings, path handling, device detection).
3. Overengineering: needless layers and wrappers, speculative options, redundant fallbacks/retries/backups, defensive code for impossible cases.
4. Size and memory: unused libraries/IRX, oversized buffers and tables, duplicate assets/fonts/strings, leaks.
5. Performance: blocking work on the UI thread, busy loops, wasted redraws, repeated scans, slow startup, needless card/disk writes.
6. Bugs and security: real defects, unchecked returns, overflows, unsafe input handling (cite them).
7. Build/CI/repo clutter: unused targets and flags, redundant workflow jobs, committed build output, stray files, unused assets, stale docs (stale branches/tags are only LISTED, by a separate step).
8. Half-finished or redundant features that could be removed.

## EVIDENCE STANDARDS (a finding that does not meet these is rejected)

- Line numbers come from the Read tool or `grep -n` on the file under `src/<Repo>/`. Give a tight range (the lines that show the problem), not the whole file. One finding may list many locations.
- Dead code (cat. 1): before claiming something is unused, search the WHOLE repo for the name: C/C++ sources and headers, assembly (`.S`, `.s`), Makefiles, `exports.tab`/`imports.lst`, linker scripts, Lua, Python, YAML, shell, workflows. Consider function pointers, dispatch tables, macros and token pasting (`##`), IRX export tables, RPC command tables, Lua bindings, `__attribute__` constructors, weak symbols, and build variants (a symbol unused in one variant may be used in another). State in `evidence` what you searched and what you found (for example: "grep -rnw LoadFoo src/ modules/ include/ Makefile: only the definition at x.c:120 and the prototype at x.h:33").
- Duplication (cat. 2): cite both (all) copies. Say how many lines are really the same and what the net reduction would be after consolidating. Do not propose a shared helper unless it removes code overall.
- Size/memory (cat. 4): say whether a number was MEASURED (name the evidence file or command) or INFERRED (give the arithmetic, for example "static char buf[65536] = 64 KB of .bss").
- Performance (cat. 5): name the thread/context the code runs in and why it blocks or repeats; cite the call path.
- Bugs/security (cat. 6): give the concrete triggering input or sequence and show the path is reachable (who calls it, with what data). "Unchecked return" needs a realistic failure consequence. No theoretical nitpicks dressed up as bugs: rate them honestly low.
- Additions: if your fix adds anything (a check, a helper, a test, an option), the `justification` field is mandatory: the concrete problem and why this is the simplest net win.
- Upstream or vendored code (FatFs, lwIP/SMSTCPIP, mbedTLS, rcheevos, codec ports, PS2SDK copies): prefer "drop the private copy / trim the config / stop compiling what is unused" over rewriting it. Say that the code is upstream-derived.
- Honest ratings. Most findings in a mature codebase are small. Do not inflate.

## RATING SCALES

- `benefit_rank` (used to sort the report):
  - 5 = major: fixes a real crash, data-loss, memory-card corruption or security bug; or removes >= 1000 lines, >= 50 KB of shipped binary, >= 100 KB RAM, or a multi-second UI freeze.
  - 4 = large: >= 300 lines removed, >= 10 KB binary, >= 32 KB RAM, a clear reliability or responsiveness gain, or a real but less severe bug.
  - 3 = moderate: >= 80 lines, >= 2 KB, a minor bug, a redundant CI job, a redundant card write.
  - 2 = small: >= 15 lines, a few hundred bytes, a small simplification.
  - 1 = trivial: a few lines, cosmetic, naming, a stale comment.
- `effort`: S (under an hour, local change), M (a few hours, several files), L (a day or more, cross-module, needs hardware testing).
- `risk`: Low (cannot change behaviour, or trivially checked), Med (touches live behaviour, needs testing), High (touches boot, storage, protocol or memory-card paths where a mistake loses data or bricks a setup).
- `confidence`: High, Med, Low. `basis`: READ (you read every cited line and ran the searches) or INFERRED (some part is reasoned, not directly verified; say which part).
